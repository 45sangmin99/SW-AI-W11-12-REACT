# Step 4 결정 기록

Step 4 요구사항 정의서(2026-11-17)의 "구현 전에 확인할 충돌·제약" 6개를 구현 전에 실측하고 정한 내용이다.
정의서가 가정하지 못한 점은 아래 **실측** 표가 근거다 (이 맥, Node 26, 생성기 시드 20261109).

## 실측: 100만 건을 그대로 처리하면

| 항목 | 결과 |
| --- | --- |
| 생성 (`generate-sample.cjs --count 1000000`) | 4초, 180MB |
| DBMS 적재 (`db/load_sample.py`) | 13.5초 (적재 중 `mini-db` 메모리 최대 1.6GB) |
| DBMS에서 1만 행씩 읽기 | 한 페이지 약 0.68초, **전체 100페이지 약 62초** |
| 현재 `analysis.js`로 탐지 (Node) | **약 40초**, 메모리 약 950MB |
| 탐지된 신호 | 748개 중 반복 문구 747개, 기기·버전 쏠림 1개. **급증과 유형 쏠림 0개** |
| 신호 하나의 근거 문의 | 최대 25,148건 |

→ 요청 때마다 계산할 수 없고(약 100초 > 캐시 TTL 60초), 시나리오 886건은 100만 건에 묻히며, 반복 문구 기준(한 시간 10건)은 평소 문의만으로 항상 넘는다.

## 결정 6개 (모두 제안대로 확정)

| # | 쟁점 | 결정 | 상태 |
| --- | --- | --- | --- |
| 1 | 화면 계산과 서버 계산이 다름 | **Node 서비스가 `src/voc/analysis.js`를 그대로 재사용한다.** 탐지 로직이 한 벌이라 샘플 모드(브라우저)와 통합 모드(서버)의 결과가 같다. 중계기를 `tools/voc-service.mjs`로 옮겼다. | 1단계 완료 |
| 2 | 100만 건 처리 | 1만 건 이하는 요청 때 계산한다 (탐지 약 22ms). **100만 건은 백그라운드로 한 번 계산해 보관**하고 화면은 진행률을 보여 준다. 필터는 그 전체 결과에서 거른다. 생성기 시나리오 크기와 탐지 임계값을 규모에 맞게 바꾼다 (U-14 기준 변경). | 4단계 |
| 3 | alert ID와 `GET`의 쓰기 | ID는 **처음 필요할 때** 만든다(상태를 처음 바꿀 때, 상세를 열 때). `GET`은 읽기만 한다. 필터와 무관한 전체 기준 탐지의 발생 건만 저장해 필터별 오염을 막는다. | 2단계 |
| 4 | 캐시 정책이 v19 C2(유형 접두사)와 다름 | **세대 번호 방식을 채택**하고 접두사 방식은 폐기한다. 세대 번호에 서비스 시작 시각을 넣어 재시작에도 옛 키와 겹치지 않는다. | 1단계 완료 |
| 5 | 재적재 때 캐시 무효화 | `POST /api/v1/admin/invalidate`(헤더 `X-Admin-Token`, 127.0.0.1만). `db/load_sample.py`가 적재 성공 뒤 호출하고, 서비스가 꺼져 있으면 건너뛴다. | 1단계 완료 |
| 6 | 단일 인스턴스, DBMS에 UNIQUE 없음 | 한 인스턴스만 지원한다. 시작할 때 잠금 파일로 **두 번째 실행을 거부**해서 코드로 강제한다. | 1단계 완료 |

## 정의서와 다르게 구현한 곳 (이유와 함께)

| 정의서 | 구현 | 이유 |
| --- | --- | --- |
| 신호마다 이력 키 `cache:voc:v1:alert:{id}:history:{gen}` | 모든 신호의 이력을 한 키 `cache:voc:v1:statuses:{gen}` | 목록과 상태 필터가 모든 신호의 현재 상태를 한꺼번에 필요로 한다 |
| 조회 조건 `from`, `to` | `period`(`all`/`24h`/`3d`/`7d`) | 화면의 기존 기간 필터와 탐지 규칙(기간 필터는 탐지 뒤에 적용)을 그대로 쓰려고 |
| `GET /alerts`의 `currentStatus`를 분석 캐시에 포함 | 카드는 상태 없이 캐시하고 응답을 만들 때 상태를 합친다 | 상태를 바꿀 때 분석 캐시까지 비우지 않으려고 |
| 기존 세 경로를 호환 어댑터로 | 화면은 `/api/v1`만 쓰고, 예전 `tools/dev-proxy.py`는 파일로만 남김 | 새 서비스가 같은 주소(8001)를 쓴다 |
| 필드 이름 camelCase | 응답은 camelCase, 문의 레코드 필드는 기존 snake_case 유지 | 문의 스키마(R-09)를 바꾸지 않으려고 |

## 남은 확인 사항 (정의서 안의 어긋남)

- U-27은 측정 모드를 3개(DBMS 직접, Redis HIT, Redis MISS)로, S4-16과 `/performance`는 4개(index, scan, redis-hit, dbms-miss)로 적었다. 3단계에서 하나로 정해야 한다.
- 성능 측정의 "Redis MISS"는 100번 PUT하는데 Mini Redis에는 로그 재작성이 없다. 측정 값의 크기를 작게 하거나 측정 전용 키를 써야 한다.
- 인덱스 대 스캔 측정은 100만 건에서 한 번에 약 0.5초 이상이라, 요청 안에서 100번 돌리지 말고 미리 측정해 둔 결과를 보여 주는 방식이 필요하다.
- `alert_status_history.alert_id`를 `INT`로 바꿀 수 있는지(DBMS는 `ALTER TABLE`이 없다)는 2단계에서 확인한다.
