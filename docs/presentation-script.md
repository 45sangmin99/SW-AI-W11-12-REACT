# 미니 리액트 발표 대본 (약 13분)

> 읽는 법: **[화면]** = 지금 띄울 것, **[말]** = 그대로 읽어도 되는 대사, **[팁]** = 대사에 없는 주의사항.
> 대사는 말투를 편하게 바꿔도 된다. 단, 굵게 표시한 **핵심 문장**은 그대로 말하는 것을 권한다.

## 발표 전 준비 (5분 전)
1. 프로젝트 폴더에서 터미널을 열고 서버 실행: `python3 -m http.server 8000`
2. 브라우저 탭 3개를 미리 열어 둔다.
   - `http://localhost:8000/index.html` (데모)
   - `http://localhost:8000/test.html` (단위 테스트 결과)
   - VS Code에서 `src/diff.js`와 `src/mini-react.js`를 열어 둔다.
3. `index.html`의 테스트 영역 코드 칸에 복사해 둘 문장을 메모장에 준비한다.
   ```
   <h1 class="title big">Hi</h1><ul><li>A</li><li>B</li><li>C</li></ul><b>old</b>
   ```
   > [팁] 데모는 마지막에 "이 문장을 붙여 넣고 Patch"만 하면 된다. 직접 타이핑하다 오타 나는 것을 막는다.

## 1. 오프닝 (1분)

**[화면]** 빈 화면 또는 제목 슬라이드

**[말]**
"안녕하세요. 오늘은 저희가 만든 미니 리액트를 설명드리겠습니다.
먼저 질문 하나 드릴게요. 화면에 글자 하나만 바뀌었는데, 페이지 전체를 지우고 다시 그리면 어떤 문제가 생길까요?
느려지고, 입력 중이던 칸의 포커스도 날아갑니다. 그래서 **'무엇이 바뀌었는지 알아내서, 바뀐 곳만 고친다'**는 것이 오늘 이야기의 전부입니다.
이걸 해 주는 게 Virtual DOM, Diff, Patch입니다. 그리고 이걸 상태 변화에 자동으로 연결해 주는 게 컴포넌트와 Hooks입니다."

**[말] 구조 안내**
"순서는 데모, Phase 1, Phase 2, 설계에서 신경 쓴 점, 마지막으로 한계 순서입니다."

## 2. 라이브 데모 (2분)

**[화면]** `index.html`

**[말]**
"왼쪽이 실제 영역, 오른쪽 위가 코드를 고치는 칸, 그 아래가 테스트 영역 미리보기입니다. 버튼은 Patch, 뒤로가기, 앞으로가기 세 개입니다."

**[동작 1]** 코드 칸에서 `Hello`를 `Hi`로 바꾼다 → 미리보기만 바뀌고 실제 영역은 그대로.
**[말]** "코드를 고치면 테스트 영역 미리보기만 바뀝니다. 실제 영역은 아직 그대로죠."

**[동작 2]** **Patch** 클릭 → 실제 영역이 바뀐다.
**[말]** "Patch를 누르면 실제 영역이 같아집니다. **여기서 중요한 건, 바뀐 글자만 고쳐졌다는 겁니다.**"

**[동작 3]** 메모장의 문장을 코드 칸에 붙여 넣고 Patch → 여러 부분이 한 번에 바뀐다.
**[말]** "이번엔 속성, 텍스트, 추가, 삭제가 한 번에 섞여 있습니다. 그래도 한 번에 반영됩니다."

**[동작 4]** 뒤로가기 → 앞으로가기
**[말]** "뒤로가기를 누르면 실제 영역과 테스트 영역이 같이 이전 상태로 돌아갑니다. 맨 처음에서는 버튼이 비활성화돼서 더 못 가게 했습니다."

**[팁]** 시간이 남으면 개발자 도구(F12)에서 `h1`을 선택한 채 Patch를 눌러 보여 준다. "이 노드가 교체되지 않고 값만 바뀝니다"라고 말하면 임팩트가 크다.

## 3. Phase 1: Virtual DOM → Diff → Patch (4분)

**[화면]** 화이트보드 또는 슬라이드에 아래 그림 하나만

```
HTML ─①변환→ Virtual DOM(이전) ─┐
                               ├─②diff→ 변경 목록 ─③patch→ 실제 DOM
HTML ─①변환→ Virtual DOM(새것) ─┘
```

**[말]**
"방금 데모 뒤에서는 세 단계가 돌았습니다. 변환, 비교, 반영입니다."

### ① 변환 (1분)
**[화면]** `src/vdom.js`의 `domToVdom` 함수

**[말]**
"먼저 변환입니다. 실제 DOM을 이런 일반 객체로 바꿉니다. 태그, 속성, 자식이 들어 있는 객체예요.
왜 바꾸냐면, **실제 DOM을 직접 비교하는 건 느리고, 비교 결과를 데이터로 남기기도 어렵기 때문입니다.** 객체로 바꾸면 빠르게 비교할 수 있고 저장도 됩니다."

**[팁]** 코드를 줄별로 읽지 말고 "요소는 `tag, props, children`, 텍스트는 `value`"만 짚는다.

### ② Diff (2분) ← 가장 중요
**[화면]** `src/diff.js` (60줄 정도라 한 화면에 들어온다)

**[말]**
"두 번째가 Diff입니다. 이전 트리와 새 트리를 **같은 위치끼리** 비교합니다. 그리고 DOM을 직접 고치지 않고, **'무엇을 어디서 어떻게 바꿀지' 목록만 만듭니다.**
바뀌는 경우는 딱 다섯 가지입니다. 추가, 삭제, 타입 교체, 속성 변경, 텍스트 변경이요."

**[화면]** `docs/walkthrough.md`의 변경 목록 예시 (5개짜리 배열)

**[말]**
"데모에서 마지막에 붙여 넣은 문장을 비교하면 이런 목록이 나옵니다. h1의 속성, h1의 글자, li 추가, p를 b로 교체, i 삭제.
**주목할 점은, 바뀌지 않은 ul과 앞의 li 두 개는 이 목록에 아예 나오지 않는다는 겁니다.** 그래서 DOM에서도 손대지 않습니다."

### ③ Patch (1분)
**[화면]** `src/patch.js`의 `patch` 함수

**[말]**
"세 번째가 Patch입니다. 변경 목록을 앞에서부터 하나씩 적용합니다. 각 변경에는 위치가 있어서, 그 위치의 DOM 노드를 찾아서 고칩니다.
**결과적으로 바뀐 노드만 갱신되고, 나머지 노드는 같은 객체 그대로 남습니다.** 이게 Virtual DOM의 존재 이유입니다."

## 4. Phase 2: 컴포넌트·상태·Hooks (4분)

**[말] 연결 문장**
"Phase 1은 'HTML을 바꿔 주는 도구'였습니다. **Phase 2는 이 도구를 상태가 바뀔 때 자동으로 돌려주는 장치입니다.** 그래서 Phase 2는 Phase 1 코드를 새로 만든 게 아니라 그대로 가져다 씁니다."

**[화면]** `src/mini-react.js` 맨 위 import 부분 (diff, patch, render를 가져오는 줄)

**[말]** "여기 보시면 diff, patch, render를 Phase 1에서 import하고 있습니다."

### 한 줄 흐름 (칠판에 쓴다)
```
setState → update() → 함수 다시 실행(새 Virtual DOM) → diff → patch → useEffect
```

### h() (30초)
**[화면]** `mini-react.js`의 `h` 함수

**[말]** "`h`는 리액트의 createElement에 해당합니다. JSX 변환기는 따로 없어서 `h`를 직접 호출해서 Virtual DOM 객체를 만듭니다."

### FunctionComponent (1분)
**[화면]** `FunctionComponent` 클래스의 `mount`와 `update`

**[말]**
"함수형 컴포넌트를 감싸는 클래스입니다. `mount`는 처음 그리기, `update`는 다시 그리기입니다.
`update`가 하는 일은 Phase 1과 똑같습니다. 새 Virtual DOM을 만들고, 이전 것과 diff하고, patch합니다."

### useState (1분 30초) ← 정의서의 핵심 질문
**[화면]** `useState` 함수, 그리고 클래스의 `hooks` 배열

**[말]**
"여기서 정의서의 핵심 질문이 나옵니다. **컴포넌트 함수는 상태가 바뀔 때마다 새로 실행되는데, 상태는 어떻게 안 사라질까요?**
답은 간단합니다. 상태가 함수 안에 있는 게 아니라, **FunctionComponent 객체의 hooks 배열에 있기 때문입니다.** 함수가 몇 번 다시 실행돼도 이 배열은 그대로 살아 있습니다.
그리고 useState는 '몇 번째 호출인지'로 자기 칸을 찾습니다.
**그래서 Hook을 if문 안에서 쓰면 안 됩니다.** 호출 순서가 바뀌면 칸이 어긋나서 상태가 엉키거든요. 저희는 호출 개수가 달라지면 에러로 막아 놨습니다."

### useEffect, useMemo (30초)
**[말]**
"useEffect는 DOM이 갱신된 뒤에 실행되고, 의존성이 바뀔 때만 다시 실행됩니다. useMemo는 계산 결과를 저장해 두고, 의존성이 같으면 다시 계산하지 않습니다."

## 5. 설계에서 신경 쓴 점 (2분)

**[말]** "구현하면서 특히 신경 쓴 세 가지만 말씀드리겠습니다."

**① 인덱스 일치**
"Virtual DOM에서는 주석과 `script`를 뺍니다. 그런데 실제 DOM에 이게 남아 있으면 자식 순서가 어긋나서 **엉뚱한 노드를 고치게 됩니다.** 그래서 같이 정리합니다."

**② 불변 스냅샷**
"뒤로가기 기록에 저장한 Virtual DOM이 나중에 몰래 바뀌면 기록이 망가집니다. 그래서 저장할 때 얼려 둡니다. 수정하려 하면 에러가 납니다."

**③ 실패한 렌더가 상태를 오염시키지 않게**
"렌더링 중에 에러가 나면, 그 렌더에서 기록하던 effect나 memo 정보가 반쯤 바뀐 채로 남을 수 있습니다. 그래서 **렌더가 성공한 뒤에만 기록을 확정합니다.**"

**[팁]** 질문이 나오면 이 세 개 중 하나를 골라 깊게 들어가라. 셋 다 말하려고 서두르지 말 것.

## 6. 한계와 실제 React와의 차이 (1분)

**[말]**
"솔직하게 한계도 말씀드리겠습니다.
첫째, **Fiber가 없습니다.** 실제 리액트는 작업을 쪼개서 중단하고 재개할 수 있는데, 저희는 동기식으로 한 번에 돌립니다.
둘째, key가 없어서 목록 순서를 바꾸면 노드를 옮기는 게 아니라 각 자리의 내용을 고칩니다.
셋째, 여러 상태 변경을 묶어서 처리하는 Batching은 선택 과제라 구현하지 않았습니다.
넷째, 상태는 최상위 컴포넌트에만 둡니다. 자식은 props만 받는 순수 함수입니다."

**[말] 마무리**
"정리하면, **바뀐 곳만 찾아서(Diff) 바뀐 곳만 고친다(Patch). 그리고 상태가 바뀌면 그걸 자동으로 해 준다(Phase 2).** 이 한 줄이 미니 리액트의 전부입니다.
추가로, 단위 테스트가 121개 있고 브라우저에서 `test.html`을 열면 바로 돌릴 수 있습니다. 테스트 페이지 주제는 팀에서 정하면 Phase 1과 2를 함께 쓰는 형태로 만들 예정입니다."

**[화면]** (선택) `test.html`을 열어 "121개 통과"를 보여 준다.

## 데모가 안 될 때의 대처
- **페이지가 하얗게 나온다** → 주소가 `file://`로 시작하면 모듈이 안 열린다. `http://localhost:8000/...`으로 다시 연다.
- **서버가 꺼졌다** → 터미널에서 `python3 -m http.server 8000`을 다시 실행한다.
- **그래도 안 된다** → `docs/walkthrough.md`를 열어 변경 목록 예시를 보여 주면서 말로 진행한다. 그림이 이미 있어서 데모 없이도 설명이 된다.
