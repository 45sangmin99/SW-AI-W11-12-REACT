VOC 프로젝트 지도

기획의도. 서버는 정상인데 고객은 불편한 문제(에러 없이 잘못 동작하는 기능, 화면 개편 후 혼란 등)는 서버 모니터링에 잡히지 않고 고객 문의로만 드러납니다. 여러 상담원에게 흩어진 문의를 모아 급증 · 유형 쏠림 · 기기·버전 쏠림 · 반복 문구를 화면에 보여 주고, 담당 팀이 신호별 진행 상태까지 남길 수 있게 했습니다.

Mini Redis · 빠르게

redis/ (C++20, HTTP)
  • 읽기 캐시: 문의 60초, 이력 10초 (TTL)
  • 메모리 해시 테이블, 요청은 이벤트 루프 하나가 직렬 처리
동시성만료 TTLHTTP API무효화AOF 복구

Mini DBMS · 믿을 수 있게

dbms/reliable/ (C)
  • 원본 저장: 문의 1만 건과 신호 상태 이력
  • SQL → B+ 트리 → 커밋 로그(WAL) → CSV, 꺼져도 확정한 변경은 남음
SQL 처리B+ 트리API 서버트랜잭션·복구

화면에서 하는 일 → 뒤에서 일어나는 일

화면에서RedisDBMS
페이지를 처음 열면문의·이력 응답이 없으니 MISS. 읽은 결과를 압축해 저장(문의 60초, 이력 10초). 화면 배지: DBMS 직접SQL로 문의와 이력을 읽음
다시 열거나 새로고침하면있으면 HIT. 바로 응답. 화면 배지: Redis 캐시호출되지 않음
신호의 진행 상태를 바꾸면DBMS 저장이 확인된 뒤에 이력 캐시를 삭제INSERT, 영구 저장(DURABLE)을 확인해야 화면에 반영
Redis를 끄면없음그대로 읽음. 화면은 똑같이 동작
DBMS를 끄면캐시 TTL이 남은 동안은 캐시로 응답할 수 있음화면에 원인이 표시됨. ?source=sample로 DB 없이 볼 수 있음
