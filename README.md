# Mini React — OBJECT NOTE 고객 문의(VOC) 이상 탐지

바닐라 JavaScript(ES Modules)로 직접 만든 미니 리액트와, 그 위에서 돌아가는 **고객 문의(VOC) 이상 탐지 페이지**.
외부 라이브러리와 프레임워크는 쓰지 않았다.

> **한 줄 요약**: `h()`로 Virtual DOM을 만들고 → 이전 것과 비교(`diff`)하고 → 바뀐 노드만 실제 DOM에 반영(`patch`)한다.
> 상태(`useState`)가 바뀌면 이 과정이 자동으로 다시 돈다. 이 위에서 문의 속 **급증 · 유형 쏠림 · 기기·버전 쏠림 · 반복 문구**를 찾아 보여 준다.

> **OBJECT NOTE는 이 프로젝트를 위해 만든 가상의 회사다.** 큐레이션 패션·라이프스타일 쇼핑몰이라는 설정이고, 실존 회사와 관계가 없다. 화면과 `data/inquiries.sample.json`의 문의는 모두 **시연용 생성 데이터**이며 실제 고객 문의가 아니다.

**문제 정의**: 서버는 정상인데 고객은 불편을 겪는 문제(에러 없이 잘못 동작하는 기능, 화면 개편 후 혼란 등)는 서버 모니터링에 잡히지 않고 고객 문의로만 드러난다. 문의는 여러 상담원에게 흩어져 들어오므로, 이를 모아 이상 패턴을 화면에 표시해 담당 팀(개발·기획)이 알아볼 수 있게 한다. 이메일·Slack 같은 실제 알림은 범위 밖이다.

이 레포는 세 과제(Mini React · Mini Redis · Mini DBMS)를 각각 별도 레포로 만든 뒤 하나로 합치는 프로젝트의 **Step 1**이다. 이 레포만으로 단독 동작한다 (데이터는 공용 샘플 JSON).

## 실행

모듈(`import`)을 쓰기 때문에 파일을 더블클릭(`file://`)하면 동작하지 않는다. 로컬 서버로 연다.

```bash
python3 -m http.server 8000
```

| 주소 | 내용 |
| --- | --- |
| `http://localhost:8000/voc.html` | **고객 문의 이상 탐지 페이지** (Phase 1·2를 활용한 테스트 페이지) |
| `http://localhost:8000/index.html` | Phase 1 검증 페이지 (실제 영역 / 테스트 영역 / Patch / 뒤로·앞으로가기) |
| `http://localhost:8000/test.html` | 단위·기능 테스트 (259개) |

샘플 데이터(`data/inquiries.sample.json`, 3,000건)는 시드를 고정한 생성 스크립트로 만든다. 같은 시드면 항상 같은 파일이 나온다.

```bash

node scripts/generate-sample.cjs --count 5000     # 건수·시드·기준일 변경 가능
```

### 컴포넌트와 상태 위치 (제약 C-01 ~ C-04)

상태와 Hook은 루트 `App`에만 있고, 나머지 컴포넌트는 props만 받는 순수 함수다 (Lifting State Up).

## 왜 가상 DOM이 필요했나 (중점 포인트)

정의서 §7.2의 중점 포인트를 순서대로, **이 프로젝트에서 실제로 어떻게 나타났는지**로 답한다.

### Phase 1 — 브라우저 / DOM / Diff

#### 1. 브라우저에서 DOM을 다루는 방법 (Document, Window)

| API | 이 프로젝트에서 쓴 곳 |
| --- | --- |
| `document.createElement` / `createTextNode` | Virtual DOM → 실제 DOM 생성 (`dom.js`의 `render`) |
| `document.createElementNS` | 차트의 SVG 요소. HTML과 네임스페이스가 달라서 `createElement`로 만들면 그려지지 않는다 |
| `TreeWalker`, `<template>.content` | 정적 HTML을 Virtual DOM으로 바꾸기 전 주석·`<script>` 정리 (`vdom.js`) |
| `setAttribute` / `removeAttribute`, 요소 프로퍼티(`value`) | 속성 변경 반영. 입력창은 속성과 프로퍼티를 함께 맞춘다 |
| `addEventListener` / `removeEventListener`, `WeakMap` | 요소마다 안정적인 리스너를 한 번만 붙이고 최신 핸들러를 `WeakMap`에 보관 |
| `Window`: `fetch`, 이벤트 루프 | 샘플 JSON 불러오기, 비동기 콜백에서의 `batch` |

#### 2. 실제 DOM의 변화를 감지하는 브라우저 API → `MutationObserver`

DOM이 실제로 얼마나 바뀌었는지는 **브라우저에게 직접 물어볼 수 있다.** `MutationObserver`는 추가·삭제(`childList`), 속성 변경(`attributes`), 글자 변경(`characterData`)을 기록으로 알려 준다.

우리 코드가 만든 변경 목록(`lastChanges`)은 "내가 그렇게 했다"는 자기 보고라서, 그것만으로는 "정말 바뀐 노드만 건드렸다"를 증명하기 어렵다. 그래서 `tests/dom-mutations.test.js`는 `MutationObserver`로 **독립적으로 관측**한다 (앱 코드에는 쓰지 않고 테스트에만 사용).

| 확인한 것 | 브라우저가 관측한 결과 |
| --- | --- |
| 글자 하나만 바뀐 `<li>` | `characterData` **1건** |
| 속성 하나(`class`)만 바뀐 `<a>` | `attributes` **1건** |
| 바뀐 게 없는 Patch | **0건** |
| 카운터 버튼 클릭 | 숫자 글자 노드 **1건** |
| 상태가 같은 채 `update()` (핸들러는 새로 만들어짐) | **0건** — 핸들러 참조 교체는 DOM을 건드리지 않는다 |
| 근거 문의 페이지 이동 | 바뀐 노드가 **모두 근거 문의 영역 안** (머리글·필터·요약·신호 목록·이유·차트는 0건) |
| 신호 선택 | 목록의 강조와 상세 영역 안만. 머리글·필터·요약은 0건 |

#### 3. 실제 DOM이 느린 이유 (Reflow / Repaint)

DOM 노드를 바꾸면 브라우저는 스타일을 다시 계산하고, 영향받는 부분의 **레이아웃을 다시 계산(Reflow)**하고, **다시 칠한다(Repaint).** 노드를 많이 건드릴수록, 그리고 레이아웃에 영향을 주는 변경일수록 비용이 커진다. 또 DOM 읽기(예: 크기 조회)를 쓰기 사이에 섞으면 브라우저가 레이아웃을 강제로 먼저 계산한다.

> 이 프로젝트는 Reflow/Repaint 시간을 **직접 측정하지는 않았다.** 대신 그 비용의 원인인 "건드려진 노드 수"를 `MutationObserver`로 측정했다 (아래 표).

#### 4. Virtual DOM — 구조와 필요한 이유

구조는 `{ type:"element", tag, props, children }` / `{ type:"text", value }`이고 key는 없다. 평범한 객체라서 만들고, 비교하고, 얼리고(`deepFreeze`), 기록할 수 있다.

**이 프로젝트에서 가상 DOM이 필요했던 이유**는 이 화면이 **"입력 한 번에 여러 영역이 동시에 바뀌지만, 입력창은 그대로여야 하는"** 화면이기 때문이다.

| 입력 | 바뀌어야 하는 곳 | 그대로여야 하는 곳 |
| --- | --- | --- |
| 문의 검색어 한 글자 | 요약 · 신호 카드 · 상세 전체 | 머리글 · **검색창(포커스, 커서, 조합 중인 글자)** |
| 기간·유형·기기·버전 필터 | 요약 · 신호 카드 · 상세 전체 | 머리글 · 나머지 필터 |
| 신호 카드 선택 | 카드 강조 · 상세 전체 | 필터 · 요약 |
| 근거 문의 페이지 이동 | 근거 문의 목록뿐 | 이유 · 차트 · 신호 카드 · 필터 |

1. **"전체를 다시 그리면" 안 되는 이유가 명확하다.** `innerHTML`로 화면을 통째로 바꾸면 검색창이 파괴되어 한 글자 칠 때마다 포커스와 한글 조합(IME)이 끊긴다. 입력창 같은 노드는 **유지**하면서 나머지만 바꿔야 한다.
2. **"무엇이 바뀌었는지"를 손으로 관리하면 조합이 폭발한다.** 입력 5종 × 영역 5개를 `getElementById(...).textContent = ...`로 맞추면 한 곳만 빠뜨려도 화면이 어긋난다. 상태에서 화면을 "그리기만" 하고 변경 계산은 Diff에 맡기면 이 문제가 없다.
3. **차트의 막대가 곧 노드다.** 차트를 직접 SVG로 그리므로(Canvas가 아니라) 막대 하나하나가 Virtual DOM 노드가 되어, 신호를 바꾸거나 데이터가 바뀌면 달라진 막대의 속성만 Patch된다.
4. **변경된 노드만 만져서 Reflow/Repaint 범위를 줄인다.**
5. **Virtual DOM은 평범한 객체라서 테스트할 수 있다.** "이 입력에서 어떤 변경이 생기는가"를 꺼내 검증한다.

**측정: 입력 한 번에 실제로 얼마나 바뀌나** (샘플 3,000건, `MutationObserver`로 관측)

| 입력 | 동작 후 전체 노드 | Diff의 DOM 변경 | 브라우저가 관측한 변경 기록 | **건드려진 노드** | 핸들러 참조 교체 (DOM 변경 아님) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 검색창에 공백 한 칸 (결과 불변) | 614 | 1 | 1 | **1** | 27 |
| 검색 "쿠폰이 적용됐다고" | 409 | 179 | 274 | 474 | 14 |
| 필터 초기화 | 614 | 179 | 274 | 474 | 14 |
| 신호 선택 (2번째 카드) | 502 | 69 | 93 | 213 | 27 |
| 근거 문의 다음 페이지 | 504 | 23 | 27 | **37** | 26 |
| 기간 "최근 24시간" | 294 | 40 | 44 | 249 | 13 |
| 유형 "로그인·계정" | 390 | 75 | 99 | 234 | 13 |
| 필터 초기화 | 502 | 91 | 115 | 445 | 13 |

같은 화면(502노드)을 통째로 새로 만들어 바꿔 끼우면 **1,002개 노드**(지우기 501 + 만들기 501)가 건드려진다.

- 결과가 달라지지 않는 입력과 근거 문의 페이지 이동은 **1개, 37개**만 건드린다. 전체 재생성(1,002개)의 0.1%, 4%다.
- 화면 내용이 크게 바뀌는 입력(필터 초기화 474개 등)은 많이 바뀐다. 변경량이 **실제로 달라진 만큼**인 것이 요점이고, 이런 입력에서는 절약이 작다. key 없는 인덱스 비교 때문에 카드 목록이 줄거나 늘 때 위치별로 내용을 덮어쓰는 탓도 있다 ([한계 1](#예상되는-문제와-한계)).
- "Diff의 DOM 변경"보다 "관측된 변경 기록"이 많은 이유: 한 번의 `REPLACE`가 노드 삭제와 추가 두 건의 기록을 만들기 때문이다.

> **속도가 근거는 아니다.** 입력 한 번의 처리(필터 + 탐지 + 렌더링 + Patch)는 2.2~27.2ms였다. 이 규모(약 290~610노드)에서는 어떤 방식이든 사람이 느끼기 어렵다. 한 환경에서 한 번 잰 값이고 첫 입력은 예열을 포함한다. Virtual DOM의 이점은 속도가 아니라 **노드 보존과 변경 최소화, 선언적인 코드**다.

#### 5. Diff 알고리즘 — 동작 방식 · 5가지 핵심 케이스 · 실제 DOM에 반영하는 방법

두 트리를 같은 위치끼리 재귀로 비교해 **변경 목록**을 만든다. DOM은 건드리지 않는다. 각 변경은 `path`(루트부터의 자식 인덱스 배열)를 가진다.

| 케이스 | 의미 | Patch가 하는 일 |
| --- | --- | --- |
| `CREATE` | 노드 추가 | 새 노드를 만들어 부모 끝에 붙인다 |
| `REMOVE` | 노드 삭제 | 그 노드를 떼어낸다 (뒤쪽 인덱스부터 지워 앞쪽 인덱스가 밀리지 않게) |
| `REPLACE` | 태그/종류가 달라짐 | 그 자리의 서브트리를 새로 만들어 갈아끼운다 |
| `UPDATE_PROPS` | 속성 변경 | 지울 속성을 먼저 지우고, 바뀐 속성을 넣는다 |
| `UPDATE_TEXT` | 글자 변경 | 텍스트 노드의 `nodeValue`만 바꾼다 |

여기에 DOM을 건드리지 않는 `REBIND`(핸들러 참조 교체)가 하나 더 있다 ([아래](#이번에-코어에-추가한-것-리뷰-주제에서-요구해서-만든-것)).

#### 6. React에서 실제 DOM을 바꿀 때 Virtual DOM과 Diff의 동작 방식

개념은 같다 (Virtual DOM 생성 → 이전 것과 비교 → 바뀐 부분만 반영). 차이는 아래 [실제 React와의 차이](#실제-react와의-차이)에 정리했다.

### Phase 2 — Component / State / Hooks

#### 1. UI를 어떻게 Component로 나눌 것인가

화면의 영역(정의서 ①~⑤)을 컴포넌트 하나씩으로 나누고, **"입력이 바뀔 때 같이 바뀌는 단위"**로 묶었다. `SignalDetail`은 이유·차트·근거 문의로 다시 나뉜다. 차트(`BarChart`)는 신호 유형이 달라도 같은 컴포넌트를 `bars`만 바꿔 재사용한다.

#### 2. State는 어디에 두는 것이 좋은가

**루트(`App`)에만 둔다** (과제 제약 C-01, C-02). 이 화면에서는 이것이 자연스럽다. 필터 5개가 요약·신호 목록·상세 **세 곳에 동시에 영향을 주기 때문에** 어느 한 자식이 상태를 가지면 나머지가 알 수 없다. 자식은 상태 없는 순수 함수이고, 이벤트는 `App`이 내려준 콜백으로 올린다 (Lifting State Up).

#### 3. setState는 상태 변경 외에 무엇을 해야 할까

`setState`는 값만 바꾸지 않는다.
1. **같은 값이면 아무것도 하지 않는다** (`Object.is`) — 불필요한 렌더링을 막는다.
2. 렌더링 중에 호출하면 **에러** — 무한 루프를 막는다.
3. 화면을 **다시 그리도록 예약한다** (`update()`: 새 Virtual DOM 생성 → Diff → Patch). batch 안이면 값만 바꾸고 렌더링은 batch가 끝날 때로 미룬다.
4. 함수형 업데이터(`set(v => v + 1)`)를 받아 **최신 값 기준으로 계산한다.**

#### 4. 여러 상태 변경을 한 번에 처리하는 방법 — Batching (선택 과제 구현)

- **문제**: 필터를 바꾸면서 페이지를 1로 되돌리면 `setState`가 두 번이라 렌더링도 두 번이고, 중간에 "새 필터 + 옛 페이지"가 잠깐 그려진다.
- **해결**: `batch(fn)` 안의 `setState`는 값만 바로 바꾸고, **가장 바깥 `batch`가 끝날 때 컴포넌트당 한 번만** 렌더링한다. 이벤트 핸들러는 자동으로 `batch` 안에서 실행된다. 이벤트 밖(`fetch` 콜백 등)은 직접 `batch(() => {...})`로 감싼다.
- 함수형 업데이터는 batch 안에서도 누적되고, 콜백에서 예외가 나도 이미 바꾼 상태는 반영한다. 한 컴포넌트의 렌더 에러가 다른 컴포넌트의 갱신을 막지 않는다.
- 기능 테스트가 "기간 변경 + 페이지 1로 = `setState` 2번이지만 렌더링은 1번"을 확인한다.

### 이번에 코어에 추가한 것 (문의 탐지 주제에서 요구해서 만든 것)

**① 이벤트 핸들러 안정화 (`REBIND`)**
- **문제**: `onClick: () => setPage(2)` 같은 핸들러는 렌더링마다 새 함수다. `!==`로 비교하면 화면이 그대로여도 매번 "변경"으로 잡힌다. 반대로 "같은 함수"로 취급해 버리면 **오래된 클로저**가 호출된다.
- **해결**: 리스너는 요소당 이벤트당 **한 번만** 붙이고, 그 리스너가 부르는 "최신 함수 참조"만 갈아끼운다. Diff는 함수→함수 변경을 `UPDATE_PROPS`가 아니라 DOM을 건드리지 않는 `REBIND`로 따로 낸다. `MutationObserver` 테스트가 "핸들러만 새로 만들어진 `update()`는 DOM 변경 0건"임을 확인한다.
- `REBIND`는 DOM을 바꾸지 않으므로 정의서의 "5가지 핵심 케이스"에 넣지 않고, `countDomChanges()`로 실제 DOM 변경과 분리해 센다.

**② Batching** — 위 [Phase 2 4번](#4-여러-상태-변경을-한-번에-처리하는-방법--batching-선택-과제-구현) 참고.

## 예상되는 문제와 한계

숨기지 않고 적어 둔다. 발표에서 질문이 나올 만한 곳이다.

| # | 한계 | 영향 | 대응 / 판단 |
| --- | --- | --- | --- |
| 1 | **key 없는 인덱스 비교.** 목록의 길이나 순서가 바뀌면 노드를 이동하지 않고 위치별로 내용을 덮어쓴다 | 신호 카드가 늘고 줄 때 최소 변경이 아니다 (필터 초기화 410노드). 내용은 정확하다 | 카드·입력창·차트는 위치가 고정이라 영향이 작다. key 기반 비교는 [차별점 후보](#차별점) |
| 2 | **전체 Virtual DOM을 매번 새로 만들고 `deepFreeze`한다** | 노드가 수천 개로 늘면 입력마다 비용이 커진다 | 근거 문의를 5건씩 나눠 노드 수를 약 290~610개로 유지한다. 큰 목록은 가상 스크롤이 필요 |
| 3 | **Batching 범위** | 이벤트 핸들러와 `batch()` 안에서만 묶인다. `fetch` 콜백에서 여러 번 `setState`하면 직접 `batch`로 감싸야 한다 | 이 앱은 데이터 로딩 콜백에서 직접 `batch`를 쓴다. 실제 React 18은 자동으로 묶는다 |
| 4 | **`setState` 값은 렌더 실패 시 롤백하지 않는다** | 렌더가 예외로 실패한 뒤에도 바꾼 상태 값은 남는다 | effect·memo 기록은 롤백한다. 상태 값 롤백은 구현하지 않았다 |
| 5 | **컴포넌트 제거(unmount)가 없다** | 제거 시 effect cleanup이 호출되지 않는다 | 이 앱은 루트 하나가 계속 떠 있어 영향 없음 |
| 6 | **"1시간"은 시계 정시 단위로 훑는다** (슬라이딩 윈도우 아님) | 12:30~13:30에 걸쳐 몰린 문의는 두 시간으로 쪼개져 각각 20건을 못 넘길 수 있다 | 정의서의 "최근 1시간"을 정시 단위로 단순화한 해석. 슬라이딩은 [후보](#차별점) |
| 7 | **"평소"가 이상 구간을 포함한다** | 과거에 이상이 있었다면 그 시각의 평균이 올라가 이후 급증을 놓치거나, 평소 비율이 올라가 쏠림을 덜 잡을 수 있다 | 14일 데이터에서 같은 시각 표본은 최대 13개다. 이상 구간 제외 평균(robust)은 후보 |
| 8 | **한 시나리오가 여러 신호를 동시에 울린다** | 정의서의 판정 정의가 겹친다: 급증하면 그 유형의 비율도 오르므로 `급증`과 `유형 쏠림`이 같이 나온다 (쿠폰 시나리오: 급증 + 유형 쏠림 + 반복 문구) | 정의서 정의를 그대로 따른 결과다. 신호를 묶거나 우선순위를 두는 것은 정의서 밖의 결정이라 하지 않았다 |
| 9 | **반복 문구는 "정규화한 문장이 정확히 같을 때"만 잡는다** | 조사만 다르거나 단어 순서가 바뀐 변형은 다른 문구로 본다 | 형태소 분석·유사도 비교는 범위 밖 |
| 10 | **심각도 기준은 샘플에 맞춰 정했다** (U-22) | 실제 데이터에서는 다시 정해야 한다 | `config.js`에서 조정 |
| 11 | **날짜·시간은 UTC** | 한국 시간대로 보면 9시간 차이가 난다 | 브라우저 시간대에 따라 결과가 달라지지 않게 한 선택 |
| 12 | **`REBIND`가 렌더링마다 핸들러 수만큼 생긴다** (13~27건) | 변경 목록이 커 보이지만 DOM을 건드리지 않는 O(1) 참조 교체다 | `countDomChanges`로 분리해 센다 |
| 13 | 차단 범위는 "정한 속성·값만"이다 | 모든 위험한 입력을 막는 것이 아니다. 예: SVG `<animate values="javascript:...">`, `style` 속성 | 문의 본문은 텍스트 노드로만 그리므로 이 앱 화면에는 해당 경로가 없다 |

## 실제 React와의 차이

| | Mini React | 실제 React |
| --- | --- | --- |
| 재렌더링 | 동기, 재귀 비교 (**Fiber 없음**) | Fiber 트리, 중단·재개 가능 |

| unmount | 없음 | 있음 (cleanup 호출) |

## 차별점

### 이미 구현한 것

| 항목 | 설명 |
| --- | --- |
| **Batching (O-01)** | 이벤트 단위로 묶어 한 번만 렌더링. "새 필터 + 옛 페이지" 중간 상태가 그려지지 않음을 테스트로 확인 |
| **핸들러 안정화 (`REBIND`)** | 클로저 문제와 "변경 없는데 변경으로 집계되는 문제"를 동시에 해결하고, 실제 DOM 변경 수를 정확히 센다 |
| **`MutationObserver` 독립 검증** | 우리 기록이 아니라 브라우저가 관측한 DOM 변경으로 "Patch가 바뀐 노드만 건드렸다 / 전체 재생성의 10% 미만"을 증명한다 |
| **재현 가능한 시나리오 데이터 + 정답지 검증** | 정의서의 시나리오 6개를 정확한 시각·건수에 심고, 탐지 결과가 정답지와 일치하며 오탐이 0건인지 테스트한다 |
| **"그대로인 영역" 검증** | 입력 후 관련 없는 영역의 DOM 노드 동일성·HTML·변경 기록을 모두 확인한다 |
| **테스트 신뢰성 확인** | 코드를 일부러 망가뜨려 테스트가 실제로 실패하는지 확인했다 (아래 [테스트](#테스트)) |
| **렌더 실패 복구 · 보안 차단** | 성공한 렌더에서만 Hook 기록 확정, 실행 경로 차단 |

| 후보 | 내용 | 효과 / 비용 |
| --- | --- | --- |
| **패치 로그 패널** | 입력할 때마다 변경 종류·건수와 바뀐 영역을 화면 한쪽에 표시(개발자 도구식) | 발표 효과 큼 · 비용 작음 (`lastChanges`가 이미 있음) |

**테스트가 실제 결함을 잡는지 확인했다.** 코드를 일부러 망가뜨려 보았다.

| 일부러 넣은 결함 | 결과 |
| --- | --- |
| 핸들러 안정화 끄기 | 의도한 5개 테스트 실패 (`MutationObserver` 테스트 1개 포함) |
| Batching 끄기 | 의도한 8개 테스트 실패 (화면 수준 "렌더링 한 번" 포함) |
| 급증의 "3배" 조건 제거 | 의도한 2개 테스트 실패 |
| 숫자를 그대로 두기(마스킹·제거 모두 없음) | **10개 실패** (샘플 정답지, 반복 문구 카드·강조 포함) |
| 기기 필터를 켜도 기기 쏠림을 계속 계산 | 화면 테스트 1개 실패 |

원복 후 전체 테스트가 모두 통과하는 것을 다시 확인했다.

- 숫자를 `#`으로 바꾸는 단계만 지워도 그 뒤의 "글자·공백이 아닌 것 제거" 단계가 숫자를 지워서 **같은 문구로 묶이는 결과는 같다.** `#`은 키를 읽기 좋게 하고 `3일째`와 `일째`를 구분하는 장치이고, 두 단계가 겹쳐서 방어한다.
- "유형 필터를 켜면 유형 쏠림을 계산하지 않는다"는 규칙을 지워도 결과가 같다 (한 유형만 남으면 평소 비율도 100%라서 차이가 0). 이 규칙은 결과를 바꾸는 것이 아니라 **불필요한 계산을 건너뛰는 안전장치**다. 기기·버전 필터의 같은 규칙은 결과를 바꾼다.

> 개발 중 브라우저가 이전 모듈을 캐시해서 "통과"가 잘못 나온 적이 있었다. 코어를 바꿔 테스트할 때는 캐시를 무시하고 새로 불러와야 한다.
