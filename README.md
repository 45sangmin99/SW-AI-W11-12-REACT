# Mini React — 리뷰 이상 패턴 탐색

바닐라 JavaScript(ES Modules)로 직접 만든 미니 리액트와, 그 위에서 돌아가는 **리뷰 이상 패턴 탐색 페이지**.
외부 라이브러리와 프레임워크는 쓰지 않았다.

> **한 줄 요약**: `h()`로 Virtual DOM을 만들고 → 이전 것과 비교(`diff`)하고 → 바뀐 노드만 실제 DOM에 반영(`patch`)한다.
> 상태(`useState`)가 바뀌면 이 과정이 자동으로 다시 돈다. 이 위에서 리뷰 속 **급증 · 평점 쏠림 · 반복 문구**를 찾아 보여 준다.

이 레포는 세 과제(Mini React · Mini Redis · Mini DBMS)를 각각 별도 레포로 만든 뒤 하나로 합치는 프로젝트의 **Step 1**이다. 이 레포만으로 단독 동작한다 (데이터는 공용 샘플 JSON).

## 실행

모듈(`import`)을 쓰기 때문에 파일을 더블클릭(`file://`)하면 동작하지 않는다. 로컬 서버로 연다.

```bash
python3 -m http.server 8000
```

| 주소 | 내용 |
| --- | --- |
| `http://localhost:8000/review.html` | **리뷰 이상 패턴 탐색 페이지** (Phase 1·2를 활용한 테스트 페이지) |
| `http://localhost:8000/index.html` | Phase 1 검증 페이지 (실제 영역 / 테스트 영역 / Patch / 뒤로·앞으로가기) |
| `http://localhost:8000/test.html` | 단위·기능 테스트 (242개) |

샘플 데이터(`data/reviews.sample.json`, 1,000건)는 시드를 고정한 생성 스크립트로 만든다. 같은 시드면 항상 같은 파일이 나온다.

```bash
node scripts/generate-sample.cjs                  # 다시 생성 (기본 시드 20261109)
node scripts/generate-sample.cjs --count 5000     # 건수·시드·기준일 변경 가능
```

│   반복 문구 [높음] │                                         │
├────────────────────┴─────────────────────────────────────────┤

└──────────────────────────────────────────────────────────────┘
 ③④⑤ 데이터 영역 공통: 로딩 / 빈 상태 / 오류 표시

| --- | --- | --- |
| 리뷰 급증 | 상품별 **일 단위 리뷰 수**가 `평균 + 2σ` 이상이면서 8건 이상인 날 | 일별 리뷰 수 (급증한 날 강조) |
| 평점 쏠림 | 한 평점이 70% 이상이면서 20건 이상 | 평점 분포 (쏠린 평점 강조) |
| 반복 문구 | 정규화한 문장이 서로 다른 리뷰 3건 이상에 등장 (8자 이상) | 일별 반복 문구 리뷰 수 |

### 컴포넌트와 상태 위치 (제약 C-01 ~ C-04)

상태와 Hook은 루트 `App`에만 있고, 나머지 컴포넌트는 props만 받는 순수 함수다 (Lifting State Up).

```
App  ← useState ×10, useEffect ×1, useMemo ×6 (전부 여기만)
├── Header · FilterBar · SummaryCard
├── SignalList
├── SignalDetail ── SignalReason · SignalChart(BarChart) · EvidenceList(Pager)
└── ReviewForm
```

자식에서 Hook을 호출하면 에러가 난다 (테스트로 확인).

## 왜 가상 DOM이 필요했나

이 페이지는 **입력 한 번에 여러 영역이 동시에 바뀌지만, 입력창은 그대로여야 하는** 화면이다.

| 입력 | 바뀌어야 하는 곳 | 그대로여야 하는 곳 |
| --- | --- | --- |
| 검색어 한 글자 | 요약 · 신호 목록 · 상세 전체 | 머리글 · **입력창(포커스, 커서, 조합 중인 글자)** · 작성 폼 |
| 신호 선택 | 목록 강조 · 상세 전체 | 필터 · 요약 · 폼 |
| 근거 리뷰 페이지 이동 | 근거 리뷰 목록뿐 | 이유 · 차트 · 신호 목록 · 필터 · 폼 |
| 리뷰 등록 | 요약 · 신호 · 상세 · 폼 | 머리글 · 필터 |

1. **"전체를 다시 그리면" 안 되는 이유가 명확하다.** `innerHTML`로 화면을 통째로 바꾸면 검색창이 파괴되어 한 글자 칠 때마다 포커스와 한글 조합(IME)이 끊긴다. 입력창 같은 노드는 **유지**하면서 나머지만 바꿔야 한다.
2. **"무엇이 바뀌었는지"를 사람이 일일이 관리하면 조합이 폭발한다.** 입력 7종 × 영역 7개를 `getElementById(...).textContent = ...`로 손으로 맞추면 한 곳만 빠뜨려도 화면이 어긋난다. 상태에서 화면을 "그리기만" 하고 변경 계산은 Diff에 맡기면 이 문제가 없어진다.
3. **차트의 막대가 곧 노드다.** 차트를 직접 SVG로 그리므로(Canvas가 아니라) 막대 하나하나가 Virtual DOM 노드가 된다. 같은 신호에서 데이터가 바뀌면 달라진 막대의 `height`만 `UPDATE_PROPS`로 고친다.
4. **변경된 노드만 만져서 Reflow/Repaint 범위를 줄인다.** DOM을 바꾸면 브라우저는 레이아웃을 다시 계산하고(Reflow) 다시 칠한다(Repaint). 바뀌지 않은 노드는 건드리지 않으므로 이 비용의 범위가 변경 부분으로 한정된다.
5. **Virtual DOM은 평범한 객체라서 테스트할 수 있다.** "이 입력에서 어떤 변경이 생기는가"를 `FunctionComponent.lastChanges`로 꺼내 검증한다. 실제 DOM만 있었다면 "머리글은 건드리지 않았다"를 증명하기 어렵다.

### 측정: 입력 한 번에 실제로 얼마나 바뀌나

샘플 1,000건, 기본 화면에서 입력을 줬을 때 `lastChanges`를 집계한 값이다. "실제 DOM 변경"은 `REBIND`(아래 설명)를 뺀 건수다.

| 입력 | 동작 후 전체 DOM 노드 | **실제 DOM 변경** | 핸들러 참조 교체 (DOM 변경 아님) |
| --- | ---: | ---: | ---: |
| 검색창 첫 글자 `p` | 517 | **1** | 19 |
| 검색어 `prod-003` 완성 | 477 | 8 | 14 |
| 필터 초기화 | 517 | 8 | 14 |
| 신호 선택 (2번째) | 273 | 134 | 19 |
| 근거 리뷰 다음 페이지 | 275 | 23 | 18 |
| 기간 "최근 7일" | 266 | 100 | 14 |
| 작성 폼에 한 글자 | 266 | **1** | 14 |

- **결과가 달라지지 않는 입력**(첫 글자 `p`처럼 모든 상품이 일치하는 검색, 작성 폼 입력)은 DOM 변경이 1건(입력값 속성)뿐이다. 결과가 달라지는 입력(`prod-003` 완성)은 그만큼 바뀐다. 어느 쪽이든 입력창은 같은 노드로 남는다.
- 신호 선택이 많은 이유는 **신호마다 차트 막대 수가 달라서**다. 90개 일별 막대가 5개 평점 막대로 바뀌며 `REMOVE`가 80건 나온다.
- 화면이 많이 바뀌는 입력은 변경이 크고, 거의 안 바뀌는 입력은 변경이 작다. 변경 건수가 "실제로 달라진 만큼"이라는 점이 요점이다.

> **속도가 근거는 아니다.** 같은 상태에서 근거 리뷰 페이지 이동은 평균 0.16ms/회(컴포넌트 실행 + Diff + Patch 포함, 200회 평균), 같은 Virtual DOM을 통째로 새 DOM으로 만드는 데는 평균 0.37ms(만들기만, 레이아웃 제외)였다. 두 값은 측정 범위가 달라 직접 비교할 수 없고, 둘 다 1ms 미만이라 **이 규모(약 270~520 노드)에서 Virtual DOM의 이점은 속도가 아니라 "노드 보존"과 "변경 최소화"**다. 측정은 한 환경에서 한 번 한 값이다.

## 기술적으로 신경 쓴 점

### Phase 1 — Virtual DOM / Diff / Patch

| 영역 | 내용 |
| --- | --- |
| **DOM 인덱스 정합** | 주석·`<script>`를 Virtual DOM에서 빼는 만큼 실제 DOM에서도 정리(`cleanContainer`)해, Virtual DOM 인덱스와 실제 DOM 인덱스가 어긋나 엉뚱한 노드를 패치하는 문제를 막는다. `<template>` 내부도 포함 |
| **불변 스냅샷** | 히스토리·직전 렌더 결과를 `deepFreeze`로 얼려, 이후 코드가 몰래 바꿔 기록이 오염되는 일을 막는다 |
| **Diff 5가지 케이스** | `CREATE` `REMOVE` `REPLACE` `UPDATE_PROPS` `UPDATE_TEXT`. 자식 삭제는 뒤에서부터 지워 앞쪽 인덱스가 밀리지 않게 한다 |
| **입력값 동기화** | `value`·`checked`는 속성과 프로퍼티를 함께 맞춘다. `<select value>`는 자식 `<option>`을 붙인 뒤 값을 적용한다 |
| **SVG** | SVG 네임스페이스로 요소를 만들고, `foreignObject` 안쪽은 HTML로 돌아간다. `xlink:href`는 네임스페이스와 함께 반영 |
| **실행 경로 차단** | `<script>` 제외, 문자열 `on*` 속성 무시, `srcdoc`, URL 속성의 `javascript:` `vbscript:` `data:text/html` 값 차단(공백·제어문자 우회 포함) |

### Phase 2 — Component / State / Hooks

| 영역 | 내용 |
| --- | --- |
| **"함수는 매번 새로 실행되는데 상태는 어떻게 유지하나?"** | 상태는 함수 안이 아니라 `FunctionComponent`의 `hooks` 배열에 있고, Hook은 **호출 순서(인덱스)**로 자기 칸을 찾는다 |
| **Hook 규칙 강제** | 호출 개수·종류·순서가 렌더링마다 달라지면 에러. 자식 컴포넌트에서 호출해도 에러 |
| **렌더 실패 복구** | effect·memo 기록은 임시(`staged`)로 모아 두었다가 **렌더링이 성공한 뒤에만 확정**한다. 렌더 중 예외가 나도 마지막 정상 렌더의 기록이 유지된다 |
| **effect 시점** | DOM 반영(Patch) **이후** 실행하고, 의존성이 바뀌면 이전 cleanup을 먼저 호출한다 |
| **의존성 비교** | `Object.is`로 항목별 비교. 생략 = 매 렌더, `[]` = 최초 한 번 |

### 이번에 코어에 추가한 것 (리뷰 페이지가 요구해서)

**① 이벤트 핸들러 안정화 (`REBIND`)**
- **문제**: `onClick: () => setPage(2)` 같은 핸들러는 렌더링마다 새 함수다. `!==`로 비교하면 화면이 그대로여도 매번 "변경"으로 잡혀서, "그대로인 영역"을 변경 목록으로 증명할 수 없다. 반대로 "같은 함수"로 취급해 버리면 **오래된 클로저**가 호출된다.
- **해결**: 리스너는 요소당 이벤트당 **한 번만** 붙이고, 그 리스너가 부르는 "최신 함수 참조"만 갈아끼운다. Diff는 함수→함수 변경을 `UPDATE_PROPS`가 아니라 DOM을 건드리지 않는 `REBIND`로 따로 낸다.
- `REBIND`는 DOM을 바꾸지 않으므로 정의서의 "5가지 핵심 케이스"에 넣지 않고, `countDomChanges()`로 실제 DOM 변경과 분리해 센다.

**② Batching (선택 과제 O-01)**
- **문제**: 필터를 바꾸면서 페이지를 1로 되돌리면 `setState`가 두 번이라 렌더링도 두 번이고, 중간에 "새 필터 + 옛 페이지"가 잠깐 그려진다.
- **해결**: `batch(fn)` 안의 `setState`는 값만 바로 바꾸고, **가장 바깥 `batch`가 끝날 때 컴포넌트당 한 번만** 렌더링한다. 이벤트 핸들러는 자동으로 `batch` 안에서 실행된다(`dom.js`의 `setEventRunner`). `batch` 밖(타이머 등)은 예전처럼 즉시 렌더링한다.
- 함수형 업데이터(`set(v => v + 1)`)는 batch 안에서도 누적된다. 콜백에서 예외가 나도 이미 바꾼 상태는 반영한다. 한 컴포넌트의 렌더 에러가 다른 컴포넌트의 갱신을 막지 않는다.

### 리뷰 페이지 설계

| 영역 | 내용 |
| --- | --- |
| **순수 로직 분리** | 탐지·필터·페이지 나누기·입력 검증을 DOM·Hook과 무관한 순수 함수(`src/review/*.js`)로 분리해 단위 테스트가 쉽다 |
| **기준값을 한곳에** | 원문이 정하지 않은 판정 기준을 `config.js`에 모았다. 바꾸고 싶으면 이 파일만 고친다 |
| **상품별 계산** | 한 상품의 급증이 다른 상품에 섞여 묻히지 않는다 (전체를 합치면 8개 상품 중 하나의 급증은 희석된다) |
| **useMemo 사용처** | 필터 결과 · 신호 계산 · 요약 · 현재 페이지 근거 리뷰 · 상품 목록. 의존 값이 바뀔 때만 다시 계산한다 |
| **데이터 흐름** | 이벤트 → `App`의 콜백 → `setState` → 새 Virtual DOM → Diff → Patch. 자식은 콜백을 호출만 한다 |
| **샘플 데이터** | 급증·쏠림·반복 사례를 시드 고정으로 의도적으로 심고, 심은 위치를 `meta.planted`(정답지)에 적었다. 탐지가 **심어 둔 6건만 정확히 찾고 오탐이 없는지** 테스트한다 |

| 영역 | 상황 | 처리 |

| | 리뷰 0건 | 빈 상태 문구 표시, 화면이 깨지지 않는다 |
| **필터** | 검색어 앞뒤 공백·대소문자 | 무시하고 같은 결과 |
| | 조건에 맞는 리뷰 없음 | 요약·목록·상세 각각 빈 상태 표시 후 조건을 지우면 복원 |
| | 평점 필터 켠 상태에서 평점 쏠림 | 한 평점만 남기면 100%라서 **쏠림 신호는 계산하지 않는다** |
| | 선택한 신호가 필터로 사라짐 | 첫 신호로 대신 선택해 상세 영역이 비지 않게 한다 |
| **신호 판정** | 기간이 14일 미만 | 평소 수준(평균·표준편차)을 알 수 없어 급증 판단 안 함 |
| | 매일 같은 건수(표준편차 0) | 튀는 날이 없어 급증 아님 |
| | z값은 높지만 건수가 8건 미만 | 소수의 우연한 튐은 급증으로 보지 않음 |
| | 표본 20건 미만 | 100%여도 쏠림 판단 안 함 |
| | 구두점·대소문자·공백만 다른 문장 | 같은 문장으로 정규화. 한 리뷰 안에서 여러 번 써도 1건 |
| | "좋아요" 같은 짧은 말 | 8자 미만은 반복돼도 이상으로 보지 않음 |
| **페이지 나누기** | 필터로 건수가 줄어 옛 페이지 번호가 범위를 벗어남 | 1~마지막으로 자동 보정. NaN·소수·문자도 1페이지 |
| | 첫/마지막 페이지 | 이전/다음 버튼 비활성화. 마지막 페이지는 나머지 건수만 |
| **리뷰 작성** | 빈 내용·공백만 / 501자 / 없는 상품 / 별점 범위 밖 | 여러 오류를 한꺼번에 필드별로 표시. 다시 입력하기 시작하면 메시지 삭제 |
| | `<img onerror=...>` 같은 HTML | 글자 그대로 보이고 요소로 만들어지지 않는다 (`textContent` 기반 렌더링) |
| **렌더링 코어** | Hook 개수·순서가 달라짐 / 자식에서 Hook 호출 | 에러 |
| | 렌더 중 예외 | 마지막 정상 렌더의 기록 유지, 다시 mount 가능 |
| | `batch` 안 예외 | 이미 바꾼 상태는 반영하고 예외는 그대로 던짐 |
| | 렌더링 중 `setState` | 에러 (무한 루프 방지) |

## 예상되는 문제와 한계

숨기지 않고 적어 둔다. 발표에서 질문이 나올 만한 곳이다.

| # | 한계 | 영향 | 대응 / 판단 |
| --- | --- | --- | --- |
| 1 | **key 없는 인덱스 비교.** 목록의 순서가 바뀌면 노드를 이동하지 않고 위치별로 내용을 덮어쓴다 | 신호 목록 재정렬·근거 리뷰 페이지 이동 때 최소 변경이 아니다. 내용은 정확하다. 포커스가 있는 입력창이 목록 안에 있으면 보존되지 않지만, 이 화면의 목록 항목에는 입력창이 없다 | 입력창·차트·폼은 위치가 고정돼 있어 영향 없음. key 기반 비교는 [차별점 후보](#차별점) |
| 2 | **전체 Virtual DOM을 매번 새로 만들고 `deepFreeze`한다** | 노드가 수천 개로 늘면 입력마다 비용이 커진다 | 근거 리뷰를 페이지로 나눠 한 번에 5건만 그리므로 노드 수가 약 270~520개로 유지된다. 큰 목록은 가상 스크롤이 필요 |
| 3 | **Batching 범위** | 이벤트 핸들러와 `batch()` 안에서만 묶인다. `setTimeout`·`fetch` 콜백에서 여러 번 `setState`하면 직접 `batch`로 감싸야 한다 | 이 앱은 데이터 로딩 콜백에서 직접 `batch`를 쓴다. 실제 React 18은 이 경우도 자동으로 묶는다 |
| 4 | **batch 안에서 읽은 상태는 이전 값** | 같은 핸들러에서 `setX(1)` 직후 `x`를 읽으면 아직 이전 값이다 | 실제 React와 같은 동작. 연속 갱신은 함수형 업데이터를 쓴다 |
| 5 | **`setState` 값은 렌더 실패 시 롤백하지 않는다** | 렌더가 예외로 실패한 뒤에도 바꾼 상태 값은 남는다 | effect·memo 기록은 롤백한다. 상태 값 롤백은 구현하지 않았다 |
| 6 | **컴포넌트 제거(unmount)가 없다** | 제거 시 effect cleanup이 호출되지 않는다 | 이 앱은 루트 하나가 계속 떠 있어 영향 없음. `useEffect`의 `cancelled` 플래그는 의존성이 바뀔 때의 cleanup용 |
| 7 | **이상 탐지 기준은 제안값이다** (U-14) | 표준편차 방식은 기간이 짧으면 z값의 최댓값이 작다(20일이면 약 4.25). 그래서 "높음"은 기간이 긴 데이터에서만 나온다 | `config.js`에서 조정. 심각도 기준(z 4·7 / 평점 80%·85% / 반복 6·10건)은 샘플에 맞춰 정한 값이라 실제 데이터에서는 다시 정해야 한다 |
| 8 | **기간 필터의 기준일 = 데이터에서 가장 최근 리뷰의 날짜** | "최근 7일"은 오늘이 아니라 데이터의 마지막 날 기준이다. 날짜는 UTC로 처리한다 | 샘플이 고정된 과거 데이터라서 필요한 결정. 새 리뷰는 현재 시각으로 등록되어 기준일이 움직일 수 있다 |
| 9 | **새 리뷰는 메모리에만 저장** | 새로고침하면 사라진다 | Step 1의 범위. Step 4에서 DBMS INSERT로 교체된다 |
| 10 | **`REBIND`가 렌더링마다 핸들러 수만큼 생긴다** (14~19건) | 변경 목록이 커 보이지만 DOM을 건드리지 않는 O(1) 참조 교체다 | `countDomChanges`로 분리해 센다 |
| 11 | 차단 범위는 "정한 속성·값만"이다 | 모든 위험한 입력을 막는 것이 아니다. 예: SVG `<animate values="javascript:...">`, `style` 속성 | 리뷰 본문은 `textContent`로만 그리므로 이 앱 화면에서는 해당 경로가 없다 |

## 차별점

### 이미 구현한 것

| 항목 | 설명 |
| --- | --- |
| **Batching (O-01)** | 이벤트 단위로 묶어 한 번만 렌더링. "새 필터 + 옛 페이지" 중간 상태가 그려지지 않음을 테스트로 확인 |
| **핸들러 안정화 (`REBIND`)** | 클로저 문제와 "변경 없는데 변경으로 집계되는 문제"를 동시에 해결하고, 실제 DOM 변경 수를 정확히 센다 |
| **재현 가능한 생성 데이터 + 정답지 검증** | 시드 고정으로 사례를 심고, 탐지 결과가 정답지와 정확히 일치하는지(오탐 0) 테스트한다 |
| **"그대로인 영역" 검증** | 기능 테스트가 입력 후 관련 없는 영역의 **DOM 노드 동일성과 HTML**이 그대로인지 확인한다 |
| **테스트 신뢰성 확인** | 코어를 일부러 망가뜨려 테스트가 실제로 실패하는지 확인했다 (아래 [테스트](#테스트)) |
| **렌더 실패 복구 · 보안 차단** | 성공한 렌더에서만 Hook 기록 확정, 실행 경로 차단 |

### 추가 구현 후보 (제안 — **아직 구현하지 않았다**)

| 후보 | 내용 | 효과 / 비용 |

| **패치 로그 패널** | 입력할 때마다 변경 종류·건수와 바뀐 영역을 화면 한쪽에 표시(개발자 도구식) | 발표 효과 큼 · 비용 작음 (`lastChanges`가 이미 있음) |
