## 1. 코치 지적사항과 이 발표의 대응

미니 리액트 발표 때 받은 피드백: **"~인 체하지 말 것", "만든 코드를 스스로 모르는 것 같다"**. 데모만 보여 주고 슬로건("리액트의 답은 이름에 있다")으로 끝낸 것이 문제였습니다.

| 지적 | 이번 발표에서 하는 것 | 이 문서에서 확인할 곳 |
|---|---|---|
| 동작만 보여 주고 끝냄 | 요청 하나가 **어느 파일의 어느 함수를 거쳐 어디에 저장되는지** 따라가며 설명 | 3, 4절 |
| 만든 코드를 모르는 것 같음 | "왜 그렇게 했나"와 "안 하면 무슨 일이 생기나"를 한 문장씩 | 3, 4절의 「왜」 칸 |
| ~인 체함 | **구현한 것과 안 한 것**을 구분해서 말함. 검증하지 않은 것은 모른다고 말함 | 5, 6절 |
| 슬로건으로 마무리 | 숫자와 시험 결과(출처 있는 것만)로 마무리 | 5절 |

## 2. 한눈에 보기

| | Mini Redis | Mini DBMS |
|---|---|---|
| 한 문장 | 메모리에 키-값을 두고 **빠르게** 읽고 쓰는 서버 | 디스크에 표를 두고 **안 잃어버리게** 저장하는 서버 |
| 언어·인터페이스 | C++20, HTTP (`PUT/GET/DELETE /keys/{key}`) | C, SQL (CLI, HTTP 서버, 콘솔) |
| 저장 위치 | 메모리 (변경 기록은 AOF 파일) | CSV 파일 + 커밋 로그(WAL) |
| 가장 중요하게 본 것 | 요청이 서로 안 막히고, 성공 응답의 뜻이 정직한가 | 꺼져도 확정한 변경이 남고, 성공의 종류를 구분하는가 |
| 코드 위치 | `redis/src/` (`engine.hpp`, `aof.hpp`, `http.hpp`, `text.hpp`, `main.cpp`) | `dbms/reliable/src/` (`sql.c`, `engine.c`, `bpt.c`, `server.c`, …) |

**둘의 공통 철학: "성공했다"는 말의 뜻을 정직하게 구분한다.** DBMS는 `DURABLE`(영구 확정) / `UNKNOWN`(알 수 없음) / `NOT_COMMITTED`를 나눠서 응답하고, Redis는 204가 "디스크 동기화 완료"가 아니라 "로그에 쓰고 메모리에 반영"이라는 점을 문서에 명시합니다.

## 3. Mini Redis 동작원리

### 요청 하나의 흐름

```
클라이언트 ──HTTP──▶ poll() 이벤트 루프 (main.cpp)
                      │ 소켓별 버퍼에 받은 바이트를 쌓는다
                      ▼
                   HTTP 파싱 (http.hpp) + JSON 검증 (text.hpp)
                      ▼
                   Keyspace (engine.hpp): 해시 테이블 + 만료 힙
                      │ 쓰기라면 먼저 AOF에 append (aof.hpp), 성공해야 메모리에 반영
                      ▼
                   응답 (204 / 200 / 404 ...)        ※ 별도 스레드가 약 1초마다 fsync
```

### 핵심 원리와 이유

| 원리 | 어떻게 구현했나 | 왜 |
|---|---|---|
| **메모리 + 해시 테이블** | 직접 만든 해시 테이블 (FNV-1a, 체이닝). `std::unordered_map` 사용 안 함 | 키로 바로 찾아 전체를 훑지 않는다. 해시 테이블 자체가 이번 과제의 구현·검증 대상이다 |
| **충돌은 체이닝, 키 전체 비교** | 같은 칸에 줄을 세우고 칸 안에서는 키를 끝까지 비교 | 충돌은 피할 수 없다(칸은 유한, 키는 무한). 해시값만 보면 틀린 값을 돌려준다 |
| **점진적 리해싱** | 부하율 0.75를 넘으면 두 배 배열을 준비하고, 요청마다 **최대 4노드/8버킷**씩 옮김 (`Keyspace::step`) | 한 번에 다 옮기면 그동안 모든 요청이 멈춘다 (이벤트 루프가 하나라서) |
| **이벤트 루프 하나** | `poll()` + 논블로킹 소켓. 연결마다 스레드를 만들지 않음 | 명령 하나가 끝까지 실행된 뒤 다음이 오므로 락 없이 값이 안 꼬인다 |
| **만료는 절대 시각 + 힙** | 만료 시각(epoch ms)을 저장, 만료가 가장 빠른 키를 힙에서 바로 찾음. 읽을 때 확인(passive), 반복당 최대 64개 정리(active, `Keyspace::expire`) | 남은 시간은 매번 줄여야 하지만 절대 시각은 비교 한 번이다. 아무도 안 읽는 키도 정리해야 하지만 한 번에 다 지우면 멈춘다 |
| **쓰기는 로그 먼저** | 레코드 전체를 AOF에 append 성공한 뒤에만 메모리에 반영. 실패하면 메모리에 반영하지 않고 이후 변경을 막는다 | 로그에 없는데 성공으로 응답하면 재시작 후 데이터가 사라진다 |
| **fsync는 백그라운드 약 1초마다** | 별도 스레드가 호출 직전의 순번을 기록해 두고 fsync, 성공한 순번까지만 "동기화됨"으로 게시 | 쓰기마다 fsync하면 느리다. 대신 **204는 fsync 완료를 뜻하지 않는다** (아래 한계) |
| **복구** | 시작할 때 파일 잠금(`flock`) → 레코드 CRC·길이·순번 검사 → 재생 → 끝에서 쓰다 끊긴 레코드만 잘라냄 | 중간 손상을 조용히 넘기면 데이터 유실을 숨긴다. 그래서 완전한 레코드의 CRC 오류는 시작을 거부한다 |
| **한도를 넘으면 거부** | 메모리 한도 초과 시 503. 데이터를 몰래 지우지 않음 | 조용한 삭제는 거짓 성공이다 |

## 4. Mini DBMS 동작원리

### 요청 하나의 흐름

```
SQL 입력 (server.c · console.c · cli.c)
   ▼
해석 (sql.c): 렉서가 글자를 토큰으로, 파서가 문법 순서를 확인해 구조로
   ▼
엔진 (engine.c · mdb_execute)
   ├─ 읽기:  WHERE id=...이면 B+ 트리(bpt.c)로 CSV 바이트 위치를 찾아 그 행만 읽기, 아니면 전체 훑기
   │         (트랜잭션 안이면 내 변경 모음과 합쳐서 보여줌)
   └─ 쓰기:  변경을 트랜잭션에 모아 둠 (아직 저장 아님)
              COMMIT 시 (commit_tx):
              ① 충돌 확인 → 커밋 로그(WAL)에 기록하고 fsync   ← 여기서 DURABLE
              ② CSV 새로 만들어 교체 + 새 B+ 트리 (install_view)
              ③ "적용 끝" 표시 기록
   ▼
꺼졌다 켜지면 (recover): 기준본 + 확정된 로그만 재생해서 CSV를 다시 만든다
```

### 핵심 원리와 이유

| 원리 | 어떻게 구현했나 | 왜 |
|---|---|---|
| **SQL을 렉서와 파서로 분리** | 렉서는 공백·따옴표·숫자 범위를 처리해 토큰을 만들고, 파서는 토큰 순서가 문법에 맞는지 확인 | 문자열 안의 `;` 같은 것을 문법으로 오해하지 않으려면 글자 처리와 문법 확인이 분리돼야 한다 |
| **B+ 트리 인덱스 (메모리)** | `id → CSV 바이트 위치`를 트리에 저장. 조회는 트리로 위치를 찾고 그 행만 읽음 | 전체 파일을 훑지 않는다. 우리가 잰 3,000건 기준 약 1 ms vs 약 5 ms |
| **로그를 먼저 쓴다 (WAL)** | 변경을 CSV에 바로 쓰지 않고 커밋 로그에 확정한 뒤 CSV 교체 | CSV를 고치다 꺼지면 반쯤 쓰인 파일이 남는다. 로그가 확정돼 있으면 재시작 후 끝까지 반영하거나 버릴 수 있다 |
| **전부 아니면 전무 (트랜잭션)** | BEGIN 이후 변경은 개인 작업 공간에 모으고, COMMIT 한 번에 로그에 확정 | 여러 문장 중 일부만 반영된 상태를 남기지 않는다 |
| **읽던 데이터가 안 바뀜 (스냅샷)** | BEGIN 시점의 CSV 버전 + B+ 트리를 계속 참조. 커밋은 새 파일을 만들어 교체 | 한 조회가 도중에 바뀌는 값을 보지 않는다 |
| **충돌은 확정 전에 거절** | 시작 버전과 현재 버전이 다르면 커밋을 오류로 거절 (낙관적 충돌 검사) | 서로 덮어쓰는 것을 막는다. 거절은 확정 전이라 재시도해도 중복되지 않는다 |
| **성공을 구분** | `DURABLE`(로그 확정) / `UNKNOWN`(I/O 실패로 알 수 없음) / `NOT_COMMITTED` | 클라이언트가 "다시 보내도 되는지"를 판단해야 한다. `UNKNOWN`을 다시 보내면 중복 저장될 수 있다 |
| **롤백한 ID도 재사용 안 함** | ID 범위(4096개씩)를 로그에 먼저 예약한 뒤 발급 | 재시작이나 롤백 뒤에 같은 ID가 두 번 쓰이는 것을 막는다. 그래서 ID가 연속이 아니다 |
| **복구는 사람 손 없이** | 기준본 CSV + 유효한 커밋 로그로 시작 시 재구성, 깨진 꼬리는 체크섬으로 잘라냄 | 재시작할 때 사람이 CSV를 고치게 만들면 안 된다 |

## 5. 우리 팀이 차별점으로 가져간 것

**공통:** "성공"의 뜻을 구분하고, 그 구분이 거짓이 아님을 **강제 종료와 실패 주입으로 확인했다**.

| | 차별점 | 근거 (출처가 있는 것만) |
|---|---|---|
| DBMS | 성공을 `DURABLE`/`UNKNOWN`/`NOT_COMMITTED`로 구분하고, 로그 확정 → CSV 교체 → 적용 표시의 **어느 단계에서 죽어도** 복구 | 실제 프로세스 강제 종료 시험. 우리가 콘솔로 돌린 시험은 **360회, 저장됐다고 답한 약 14,600건 전부 보존** (전원 차단은 아님) |
| DBMS | B+ 트리로 위치를 찾고 CSV를 직접 읽음, 결과를 선형 탐색과 대조 | 팀 README의 100만 건 실측, 우리 콘솔 측정 약 1 ms vs 5 ms (3,000건) |
| DBMS | 콘솔(`mini-db-console`)이 오류 때도 **저장됐는지 아닌지**를 밝힘 | 콘솔 시험 24개 |
| Redis | 해시 테이블 점진적 리해싱 (한 번에 4노드) | 리해싱 한 단계 최대 약 2.4~10.5 µs (`redis/README.md`) |
| Redis | 인덱스 힙 TTL (키가 힙 위치를 보유, 갱신·삭제 O(log n)) | 단위 시험에서 만료 경계(1 ms 전/정각)를 시계 주입으로 확인 |
| Redis | AOF의 CRC·순번, 꼬리 절단, **중복 소유 거부(`flock`)**, 메모리 한도 503 | 통합 12개 그룹 통과 (이 레포에서 실행해 확인) |
| Redis | **응답의 의미를 문서로 정직하게 명시**: 204는 fsync 완료가 아님 | `redis/README.md`, 한계 절 |
| 공통 | 개념을 먼저 맞추고 구현: 각자 공부 → 프롬프트 → 키워드로 동기화 → 구현 | 발표자가 구체 사례 한두 개를 준비 `[확인 필요]` |

## 6. 둘을 같이 쓸 때 (VOC 프로젝트)

```
브라우저 ──▶ 중계기(tools/dev-proxy.py) ──▶ Mini Redis(캐시)   없으면 ↘ Mini DBMS(원본)
                                          상태 저장은 DBMS가 DURABLE을 확인한 뒤에 Redis 캐시를 지운다
```

- 문의 3,000건 응답: DBMS에서 읽으면 약 28 ms, Redis에서 읽으면 약 4 ms (이 레포에서 직접 잰 한 번의 값).
- 저장이 확인된 뒤에 캐시를 지우는 이유: 순서가 반대면 그 사이 다른 요청이 옛 데이터를 다시 캐시에 채운다.
- Redis가 꺼져도 DBMS로 정상 동작한다. 원본은 DBMS가 갖는다.

## 7. 한계 (질문받기 전에 먼저 말할 것)

| 시스템 | 한계 |
|---|---|
| Redis | **204 응답은 디스크 동기화 완료가 아니다.** 전원이 꺼지면 최근 약 1초의 쓰기를 잃을 수 있다. 프로세스 강제 종료는 시험했지만 전원 차단은 검증하지 않았다 |
| Redis | `INCR`, `SET NX` 같은 원자적 명령, RESP·`redis-cli` 호환, 인증, 복제가 없다. 그래서 카운터·락 용도로는 못 쓰고 읽기 캐시로만 연결했다 |
| Redis | AOF 재작성이 없어 로그가 계속 커지고 복구 시간이 로그 길이에 비례한다 |
| Redis | 쓰기 로그 기록이 이벤트 루프 안에서 동기로 실행돼, 기록이 느리면 읽기도 기다린다 (50 ms 지연을 주입하자 GET p95가 52.9 ms) |
| DBMS | **커밋마다 CSV 전체를 다시 쓴다.** 100만 건 삽입 4.34초 중 1.52초가 이 비용이다. 바이너리 형식과 버퍼링으로 개선하는 작업은 팀원 한 명이 별도로 진행 중이다 `[확인 필요]` |
| DBMS | 전원 차단·저장장치 고장 전체는 검증하지 않았다. 이 맥에서 ASan이 초기화 단계에서 멈춰 대신 malloc 검사와 `leaks`로 확인했다 |
| DBMS | `CREATE TABLE`, `JOIN`, `NULL` 등이 없다. 테이블은 미리 준비한다 |
| 둘 다 | Linux 실행은 검증하지 않았다 (macOS) |

## 8. 코치가 물을 만한 질문 (코드 위치와 함께)

| 질문 | 한 문장 답 | 코드 |
|---|---|---|
| Redis는 왜 빠른가? | 메모리에서 해시 테이블로 키를 바로 찾는다 | `redis/src/engine.hpp` `Keyspace` |
| 해시 충돌은 어떻게 처리하나? | 체이닝으로 줄을 세우고 칸 안에서 키 전체를 비교한다 | `engine.hpp` |
| 리해싱 중에 서버가 멈추지 않나? | 한 번에 4노드씩 옮겨서 멈춤을 쪼갰다. 실측 한 단계 최대 약 10 µs | `Keyspace::step` |
| TTL은 언제 지워지나? | 읽을 때 확인하고, 안 읽는 키는 힙 맨 위부터 반복당 64개씩 | `Keyspace::expire` |
| 204면 디스크에 저장된 건가? | 아니다. 로그에 쓰고 메모리에 반영한 것이고 fsync는 약 1초마다다 | `redis/src/aof.hpp` |
| 왜 로그를 먼저 쓰나? | 로그에 없는데 성공으로 응답하면 재시작 후 사라진다 | `aof.hpp`, `engine.c` `commit_tx` |
