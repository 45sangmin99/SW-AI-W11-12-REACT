# Mini Redis 정리 노트 — 왜 그렇게 했는가

> 직접 정리한 개념에 **"왜"를 한 줄씩 붙인 문서**입니다. 표의 왼쪽은 내가 정한 것, 오른쪽은 그렇게 한 이유입니다.
> **이 문서는 일반적인 Redis 개념 노트입니다.** 우리가 실제로 만든 Redis(`redis/`)와 다른 부분은 각 절 맨 위의 「우리 구현은?」 상자와 아래 대응표에 표시했습니다. 발표에서 "우리가 구현했다"고 말하기 전에 반드시 이 표를 보세요.
> 개념이 많아 뒤죽박죽 느껴질 때는 아래 「이유의 뼈대 4개」만 먼저 보세요. 나머지 이유는 전부 이 4개 중 하나로 돌아옵니다.

## 이유의 뼈대 4개

| # | 뼈대 | 이게 만든 결정들 |
|---|---|---|
| 1 | **TCP는 메시지가 아니라 바이트의 흐름이다** | 버퍼에 쌓기, `\r\n`으로 자르기, 덜 온 데이터는 기다리기, `sendall` |
| 2 | **서버는 어떤 입력에도 죽으면 안 된다** | 인자 개수 검사, 타입 검사(INCR), 모르는 명령은 `-ERR`, 에러도 응답 한 개 |
| 3 | **싱글 스레드라 락은 필요 없지만, 오래 걸리는 일 하나가 모두를 멈춘다** | `select` 이벤트 루프, 점진적 리해싱, TTL 샘플링 삭제, `KEYS 패턴` 지양 |
| 4 | **원본은 DBMS가 갖고, Redis는 날아가도 되는 것만 둔다** | 캐시 무효화(DEL), TTL을 안전장치로, 영속성은 선택 사항 |

## 우리 구현 vs 이 노트 (`redis/README.md`를 읽고 확인)

| 노트의 개념 | 우리 Redis |
|---|---|
| RESP 프로토콜, `redis-cli` 호환 | **없음.** HTTP로 `PUT/GET/DELETE /keys/{key}`, `GET /keys/{key}/ttl` 네 가지만 제공 |
| `select()` I/O 다중화 | **`poll()`** 이벤트 루프 하나 (논블로킹, 연결별 스레드 없음) |
| `INCR`, `SET NX` (명령 하나로 원자적) | **없음.** 그래서 카운터·락 용도로는 못 쓰고 읽기 캐시로만 씀 |
| 해시 테이블 (체이닝) | **일치.** FNV-1a, 4칸에서 시작, 부하율 0.75에서 2배, **점진적 리해싱 구현** (한 번에 최대 4노드/8버킷) |
| TTL 만료 시각 + 지연 삭제 + 주기 삭제 | **일치.** 절대 시각(epoch ms) + 인덱스 힙, 읽을 때 확인, 반복당 64개 정리 |
| AOF + `fsync` 1초 | **일치(바이너리 기록).** CRC32·순번이 있는 `MRD1` 레코드, 백그라운드 1초 fsync, 시작 시 재생·꼬리 절단. **AOF 재작성은 없음** |
| 인증 | **없음** (127.0.0.1 전제) |
| 복제 | **없음** |
| 캐시 어사이드·무효화·단일 비행 | Redis 자체가 아니라 **중계기(`tools/dev-proxy.py`)** 가 구현. 락(`SET NX`)이 없어 단일 비행은 중계기 프로세스 안의 락으로 대신함 |

## 0. 전체 흐름

> **우리 구현은?** 6단계 중 ①②③⑥의 모양이 다릅니다. 수신은 `poll()`, 파싱은 HTTP(`http.hpp`)와 엄격한 JSON(`text.hpp`), 디스패치는 메서드+경로 네 개, 직렬화는 JSON과 상태 코드입니다. 해시 테이블과 TTL(④⑤)은 노트와 같습니다.

`네트워크 수신 → 프로토콜 파싱 → 디스패치 → 해시 테이블(+TTL) → 응답 직렬화 → 네트워크 송신`

| 정한 것 | 왜 |
|---|---|
| 단계를 이렇게 6개로 나눔 | 각 단계가 하나의 일만 알아야 한 곳만 고치면 된다. 네트워크가 바뀌어도 해시 테이블은 그대로, 명령을 추가해도 파서는 그대로 |
| 핸들러는 소켓을 모르고 값만 돌려줌 | 소켓과 섞이면 핸들러를 소켓 없이 테스트할 수 없다 |

## 1. 네트워크 (TCP 소켓)

> **우리 구현은?** `select()` 대신 `poll()`을 씁니다 (논블로킹 소켓, 같은 목적). 구분자 `\r\n` 대신 HTTP 헤더와 `Content-Length`로 경계를 잡습니다. 연결 256개, 무활동 10초, 입력 한도로 느리거나 큰 클라이언트를 막습니다.

| 정한 것 | 왜 |
|---|---|
| 받은 바이트를 **버퍼에 쌓고** `\r\n`으로 자름 | TCP는 경계가 없는 바이트 흐름이라 명령이 붙거나 잘려서 온다. 로컬 테스트에서는 잘 되다가 빠르게 연달아 보내면 터지는 버그가 숨는다 |
| `recv()`가 `b''`를 주면 연결 종료로 처리 | 상대가 연결을 끊었다는 유일한 신호다. 무시하면 빈 소켓을 계속 붙잡고 서버가 헛돈다 |
| 문자열 `"SET"`을 `b"SET"`(바이트)로 바꿔 보냄 | 네트워크로는 바이트만 갈 수 있다. 문자열은 파이썬 내부 표현일 뿐이다 |
| `select()`로 준비된 소켓만 처리 (I/O 다중화) | `accept()`와 `recv()`는 올 때까지 그 자리에서 멈춘다. 하나를 기다리는 동안 다른 손님이 멈추기 때문이다 |
| 손님(연결 소켓)마다 버퍼를 따로 둠 | 손님 A의 덜 온 데이터와 B의 데이터가 섞이면 안 된다 |
| 리스닝 소켓과 연결 소켓을 구분 | 리스닝은 "새 손님 도착", 연결은 "손님이 말함"이라 할 일이 다르다 |
| 주소·포트를 환경변수 설정으로 뺌 | 나중에 레포 셋을 하나로 합칠 때 코드를 안 고쳐도 된다 |

## 2. 프로토콜 파싱

> **우리 구현은?** RESP가 아니라 **HTTP/1.1의 일부**를 파싱합니다. 노트의 원칙(덜 온 데이터는 기다림, 여러 요청이 붙어 와도 처리, 길이는 바이트 기준, 잘못된 입력에도 서버는 계속)은 그대로 적용됐습니다. 예: 3바이트씩 쪼개 보내기, 파이프라인 10개의 응답 순서(FIFO), `Transfer-Encoding: chunked` 거부는 통합 시험에 있습니다.

| 정한 것 | 왜 |
|---|---|
| 파서 결과를 **완성 / 부족 / 잘못됨** 세 가지로 나눔 | 덜 온 데이터는 에러가 아니라 "기다림"이다. 에러로 처리하면 정상 명령이 중간에 끊겨 버린다 |
| 부족하면 버퍼를 그대로 두고 다음 `recv()`에서 이어 붙임 | 지금 버리면 나머지 반쪽이 와도 완성할 수 없다 |
| `if`가 아니라 **`while`**로 완성된 명령이 없을 때까지 꺼냄 | `PING\r\nPING\r\n`이 한 번에 오면 응답도 두 번 가야 한다 |
| 길이는 글자 수가 아니라 **바이트 수** | 한글 한 글자는 여러 바이트다. 바이트로 자른 뒤에 `decode()`해야 어긋나지 않는다 |
| 파서를 네트워크 코드와 분리된 순수 함수로 | 소켓 없이 문자열만 넣어 테스트할 수 있다 |
| 잘못된 입력도 서버가 죽지 않고 에러 응답 | 한 손님의 이상한 입력이 다른 손님 전부를 끊으면 안 된다 |
| 명령어를 `.upper()`로 통일, 빈 줄은 무시 | `set`, `SET`, `Set`을 같은 명령으로 취급해야 사용하기 편하다 |
| 두 번 자름: ① 명령 단위(`\r\n`) ② 명령 안(`["SET","name","kim"]`) | ①은 TCP가 경계를 안 줘서, ②는 핸들러가 "무슨 명령에 어떤 값"을 알아야 해서 |
| 프로토콜을 **RESP**로 고름 (띄어쓰기 방식 아님) | 띄어쓰기 방식은 값에 공백이 들어가면 깨진다. RESP는 길이를 붙여서 어떤 값도 안전하고, 진짜 Redis 도구(`redis-cli`)를 그대로 쓸 수 있다 |

## 3. 명령어 처리 (디스패치)

> **우리 구현은?** 명령 표 대신 **메서드 + 경로 네 개**입니다. `INCR`, `SET NX`, 모르는 명령에 `-ERR`로 답하는 부분은 해당 없습니다. 모르는 메서드는 405, 경로는 404입니다.

| 정한 것 | 왜 |
|---|---|
| 명령 이름 → 함수를 **표**로 연결 | 명령 추가 시 함수 하나 + 표에 한 줄이면 끝난다. 고치는 곳이 한 군데라야 실수가 안 난다 |
| 핸들러 맨 앞에서 **인자 개수 검사** | 파서는 형식만 보고, "이 명령은 인자가 몇 개"는 모른다. 검사 없이 `args[1]`을 읽으면 서버가 죽는다 |
| **없음(None)** 과 **빈 값(`""`)** 을 구분 | 둘을 똑같이 주면 "캐시에 없으니 DBMS에서 가져오자"를 판단할 수 없다 |
| `INCR`에서 숫자가 아니면 에러 응답 | `SET count hello` 후 `INCR count`에 서버가 죽으면 안 된다 |
| 모르는 명령은 `-ERR` | 공식 도구가 `HELLO`, `CLIENT` 같은 명령을 먼저 보내는데, 에러로만 답하면 계속 연결된다 |
| `INCR`에 락이 필요 없음 | 싱글 스레드라 명령 하나가 끝까지 실행된 다음에 다음 명령이 오기 때문이다 |

## 4. 해시 테이블

> **우리 구현은?** 노트와 같고, 점진적 리해싱을 **실제로 구현**했습니다. 아래 "로드 팩터 > 1이면 2배"는 개념 설명이고, 구현은 **0.75**에서 두 배 배열을 준비하고 연산마다 최대 4노드를 옮깁니다.

| 정한 것 | 왜 |
|---|---|
| 키 비교를 반드시 함 (해시값만 보지 않음) | 충돌은 피할 수 없다(비둘기집 원리: 칸은 유한, 키는 무한). 같은 칸의 다른 키를 틀리게 돌려주면 버그를 찾기도 어렵다 |
| `set`에서 같은 키가 있으면 **덮어쓰기** | 안 그러면 `SET a 1`, `SET a 2` 뒤에 체인에 `a`가 두 개 생긴다 |
| `delete`는 체인에서 **그 키만** 뺌 | 같은 칸의 다른 키까지 지우면 안 된다 |
| 충돌 처리는 **체이닝** | 삭제가 잦은 캐시에서는 개방 주소법의 "삭제됨 표시"가 쌓여 느려진다. 구현도 쉽다 |
| 로드 팩터(키 수 ÷ 칸 수)가 **1을 넘으면** 칸을 2배로 | 한 칸에 키가 몰리면 O(1)이 O(n)이 된다 |
| 리해싱은 모든 키를 **다시 배치** | `hash % 칸수` 결과가 칸 수가 바뀌면 달라진다 |
| 리해싱을 **점진적으로** (진짜 Redis 방식) | 싱글 스레드라 한 번에 오래 걸리면 모든 손님이 멈춘다 ※ 키가 적고 혼자 쓰면 한 번에 해도 충분하다 |
| 뻐꾸기 해싱은 쓰지 않음 | 일정한 조회 속도가 꼭 필요할 때만 쓴다. 우리 쓰임에는 과하다 |
| 저장소는 `set/get/delete/exists`만 제공 | 명령어와 소켓을 모르게 해서 단계 간 경계를 지킨다 |

## 5. TTL (만료)

> **우리 구현은?** 값 테이블과 만료 테이블을 따로 두는 대신, **엔트리가 힙 위치를 들고 있는 인덱스 힙**으로 만료가 가장 빠른 키를 바로 찾습니다. 절대 시각, 지연 삭제, 주기 삭제(반복당 64개)는 같습니다.

| 정한 것 | 왜 |
|---|---|
| **남은 시간이 아니라 만료 시각**을 저장 | "지금 > 만료 시각"인지 한 번만 비교하면 된다. 남은 시간은 매번 줄여야 한다 |
| 값 테이블과 만료 테이블을 **따로** | TTL 없는 키가 대부분이라 따로 두는 게 깔끔하고 메모리도 아낀다 |
| **Lazy 삭제**: 꺼낼 때 먼저 만료 확인 | 만료된 값을 주면 틀린 데이터가 나간다. 확인 후 값과 만료 시각을 둘 다 지우고 `None` |
| **주기적 삭제**: 일부만 샘플링해서 지움 | Lazy만 하면 아무도 안 읽는 키가 메모리에 남는다. 한 번에 다 지우면 싱글 스레드가 멈춘다 |
| `SET`으로 다시 저장하면 TTL 사라짐, `INCR`은 TTL 유지 | 진짜 Redis의 기본 동작과 맞춘다 (쓰던 사람이 그대로 쓸 수 있게) |
| `DEL`은 값과 만료 시각 둘 다 삭제 | 만료 시각만 남으면 같은 키로 다시 저장했을 때 엉뚱하게 만료된다 |

## 6. 응답 직렬화

> **우리 구현은?** RESP 대신 **JSON + HTTP 상태 코드**입니다 (`PUT` 204, `GET` 200 `{"value":"..."}`, 없거나 만료된 키는 404). 없음(nil)은 404, 빈 문자열은 200 `""`로 구분합니다. `sendall` 대신 비차단 쓰기로 조금씩 보냅니다.

| 정한 것 | 왜 |
|---|---|
| 종류별로 다른 형식 (`+OK` `$길이` `:정수` `-ERR` `$-1`) | 클라이언트가 문자열인지 숫자인지 없음인지 에러인지 알아야 한다 |
| 길이는 **바이트 수** | 파서와 같은 이유 (한글 등) |
| `send()`가 아니라 **`sendall()`** | `send()`는 일부만 보내고 끝날 수 있다. 응답이 중간에 잘리면 클라이언트 파서가 깨진다 |
| **요청 하나에 응답 정확히 하나, 순서대로** | 에러라고 응답을 생략하면 다음 응답이 한 칸씩 밀려 클라이언트가 엉뚱한 답을 받는다 |
| 변환을 `serialize()` **한 곳**에 모음 | 핸들러가 각자 바이트를 만들면 형식이 제각각이 된다 |

## 7. 동시성

> **우리 구현은?** 이벤트 루프 하나가 요청을 처리해서 서버 안 경합은 없습니다 (노트와 같음). 하지만 **`INCR`, `SET NX`가 없습니다.** 그래서 노트의 "읽고 계산하고 쓰기를 명령 하나로"는 개념으로만 공부했고, 우리 Redis로는 원자적 카운터나 락을 만들 수 없습니다.

| 정한 것 | 왜 |
|---|---|
| **싱글 스레드 이벤트 루프** | 서버 안에서 두 스레드가 같은 해시 테이블을 고치다 꼬이는 문제(리해싱 중 읽기 포함)가 아예 생기지 않는다 |
| "읽고 → 계산 → 쓰기"를 **명령 하나로** (`INCR`, `SET NX`) | `GET` 후 `SET`은 두 명령 사이에 다른 손님이 끼어들 수 있다. 싱글 스레드라도 이건 막지 못한다 |
| VOC 카운터는 반드시 `INCR` | 문의가 몰릴 때(이상 탐지가 가장 중요한 순간) `GET`+`SET`이면 숫자가 적게 세어진다 |

## 8. 캐시 만료 순간 대응

> **우리 구현은?** 중계기가 ①번(캐시 어사이드)을 쓰고, 같은 키의 동시 MISS는 ②번과 비슷하게 **한 요청만** DBMS에 보냅니다. `SET NX` 락 대신 중계기 프로세스 안의 락입니다 (중계기가 하나일 때만 성립).

| 방식 | 언제 | 대가 |
|---|---|---|
| ① 캐시 어사이드 (`nil`이면 DBMS에서 가져와 저장) | 기본값. 가장 단순 | 만료 순간 요청이 몰리면 DBMS에 한꺼번에 몰림 |
| ② 락(`SET lock 1 NX EX 5`)으로 한 명만 조회 | DBMS 폭주를 막아야 할 때 | 나머지는 잠깐 기다림 |
| ③ 만료 전에 미리 갱신 | `nil`을 거의 보고 싶지 않을 때 | `TTL` 명령과 로직이 늘어남 |
| ④ 옛 값을 먼저 주고 뒤에서 갱신 | 사용자가 기다리면 안 될 때 | 잠깐 옛 데이터가 보임 |
| ⑤ 쓸 때 같이 갱신 | 항상 최신이어야 할 때 | 쓸 때마다 할 일이 늘어남 |

## 9. 외부에서 쓰기 (API 설계)

> **우리 구현은?** 노트의 "진짜 Redis와 같은 규칙(RESP)"은 **채택하지 않았습니다.** HTTP API라 `redis-cli`와 공식 라이브러리는 못 씁니다. "React → HTTP → 백엔드 → Redis" 구조(브라우저가 직접 붙지 않음)는 같습니다 (`tools/dev-proxy.py`). 키 이름은 `cache:voc:inquiries`, `cache:voc:status-history`를 씁니다.

| 정한 것 | 왜 |
|---|---|
| 진짜 Redis와 **같은 규칙**(RESP, 같은 명령 이름) | 쓰던 사람이 코드를 거의 안 고치고 바꿔 끼울 수 있고, `redis-cli`로 바로 테스트된다 |
| React는 **백엔드를 거쳐서** 접근 (React → HTTP → 백엔드 → Redis) | 브라우저는 TCP 소켓을 직접 못 연다. 직접 열 수 있어도 누구나 `DEL`을 보낼 수 있어 위험하다 |
| 클라이언트 라이브러리는 **연결 하나를 재사용** | 명령마다 `connect()`하면 연결 비용이 매번 들고 서버에 소켓이 쌓였다 닫힌다 |
| 클라이언트도 직렬화(명령)와 파싱(응답)을 가짐 | 서버와 방향만 반대이기 때문이다 |
| 키 이름 규칙을 `:` 구역으로 문서화 (`voc:count:app:2.3`) | 팀원 셋이 제각각 이름 지으면 같은 데이터를 못 찾는다 |

## 10. 캐시 무효화

> **우리 구현은?** ②번과 "DBMS 먼저, 그다음 지움", "TTL은 안전장치"를 그대로 적용했습니다. ④번 버전 키 대신 **중계기 안에서 무효화 횟수를 세어**, 읽는 도중 무효화되면 그 읽기를 캐시에 저장하지 않게 했습니다 (중계기가 하나일 때만 성립).

| 정한 것 | 왜 |
|---|---|
| TTL만으로 부족하면 **직접 무효화** | TTL 60초면 최대 50초 동안 화면에 틀린 데이터가 남는다. "방금 몰린 문의가 안 보이는" 상황이 곤란하면 못 기다린다 |
| **DBMS에 먼저 저장, 그다음 캐시 삭제** | 순서가 반대면 그 사이에 다른 요청이 옛 DB 값을 다시 캐시에 채워 넣을 수 있다 |
| `cache:voc:*` 패턴 일괄 삭제는 피하고 **버전 키** 사용 | 패턴은 모든 키를 훑어야 해서 싱글 스레드가 그동안 멈춘다. 버전만 `INCR`하면 옛 키는 아무도 안 찾고 TTL로 사라진다 |
| 무효화를 해도 **TTL은 안전장치로 유지** | 무효화 코드에 버그가 있어도 최악의 경우 TTL 후 맞는 데이터로 돌아온다 |

## 11. 영속성 (서버가 죽어도 데이터 유지)

> **우리 구현은?** AOF를 구현했습니다. 다만 노트와 다른 점이 있습니다. ① RESP 텍스트가 아니라 **바이너리 레코드**(CRC32, 순번)입니다. ② **성공 응답(204)은 fsync 완료가 아니라** 로그에 쓰고 메모리에 반영한 시점입니다. 전원이 꺼지면 최근 쓰기를 잃을 수 있습니다. ③ 로그에 만료 시각(절대 시각)을 저장하는 것은 노트와 같습니다. ④ AOF 재작성과 복제는 없습니다.

| 정한 것 | 왜 |
|---|---|
| Redis는 RAM이라 **휘발성** | 빠른 이유이자 꺼지면 사라지는 이유다 (RAM vs 디스크) |
| "최대한 안전"이면 **AOF(명령 로그)** | RDB 스냅샷은 마지막 저장 이후(몇 분치)를 잃는다. AOF는 최대 1초 또는 거의 안 잃게 설정할 수 있다 |
| AOF는 **바꾸는 명령만** 파일 끝에 추가 | 읽는 명령은 상태를 안 바꾼다. 추가만 하면 쓰기가 빠르고 중간에 죽어도 앞부분이 안 깨진다 |
| `write()` 뒤에 **`fsync`**, 보통 **1초마다** | `write()`만으로는 OS 메모리에만 있어 전원이 나가면 날아간다. 명령마다 `fsync`는 가장 안전하지만 느려서, 최대 1초 손실을 받아들이는 절충을 쓴다 |
| 로그에는 `EX 60`이 아니라 **만료 시각(`EXPIREAT`)** | 재시작해서 로그를 다시 실행하면 "60초"가 처음부터 다시 시작해 이미 죽었어야 할 키가 되살아난다 |
| AOF를 **RESP 그대로** 저장 | 복구할 때 이미 만든 파서와 디스패치를 재사용한다 (단계를 나눠 둔 덕분) |
| 디스크까지 고장 나면 **복제** | AOF도 같은 디스크에 있어 소용없다. 다른 서버에 복사본이 필요하다. 지금 단계에서는 나중으로 미룸 |
| VOC에서는 영속성이 꼭 필요하지 않을 수 있음 | 목록 캐시는 DBMS로 다시 만들면 되고, 락은 몇 초짜리고, 카운터도 DBMS에서 다시 셀 수 있다. **원본은 DBMS가 지키는 것이 진짜 안전장치**다 |

## 발표에서 막힐 때 쓰는 한 문장

- 왜 버퍼에 쌓나? → TCP는 바이트의 흐름이라 명령 경계가 없어서.
- 왜 싱글 스레드인가? → 락 없이 충돌을 막을 수 있어서. 대신 오래 걸리는 일을 쪼개야 한다.
- 왜 TTL은 만료 시각인가? → 재시작해도, 비교할 때도 한 번의 비교로 끝나서.
- 왜 `INCR` 같은 명령이 필요한가? → `GET`+`SET` 사이에 다른 손님이 끼어들 수 있어서. (우리 Redis에는 이 명령이 없어서 카운터에는 못 쓴다.)
- 왜 `select`가 아니라 `poll`인가? → 같은 목적(준비된 소켓만 처리)이고, 우리는 `poll()`로 구현했다.
- 204 응답이 오면 디스크에 저장된 건가? → 아니다. 로그에 쓰고 메모리에 반영한 시점이고, fsync는 약 1초마다 백그라운드로 한다.
- 왜 DBMS 먼저 저장하나? → 순서가 반대면 캐시가 옛 값으로 다시 채워질 수 있어서.

> 이 문서는 개념 정리이고, 실제 구현과의 차이는 맨 위 「우리 구현 vs 이 노트」 표를 기준으로 합니다. 그 표는 `redis/README.md`를 읽고 만들었으며, 소스 전체를 줄 단위로 검증한 것은 아닙니다 (시험은 `make -C redis test`로 통과를 확인했습니다).
